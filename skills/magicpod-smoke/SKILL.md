# MagicPod スモークテスト作成

MagicPod MCP Server のツールを使って、アプリの核心機能だけを確かめるスモークテスト（数本の最低限のテスト）を対話しながら設計し、MagicPod に作成して、実際に動くところまで確認する。使う人は MagicPod を初めて触る人が多いので、説明は短く分かりやすくする。

進め方の原則：
- ユーザーへの質問は簡潔に、1回に1〜2項目まで。
- テストケースを作る前に、シナリオ案を見せて了承をもらう。例外は、モバイルアプリでどんなアプリか分からないときの1本目（「アプリ起動」）だけ（ステップ2参照）。
- 推測で作らない。ロケータ・表示テキスト・テストデータは、実際の画面（`capture_ui`）かソースコードで確かめた値を使う。
- まず1本だけ作って最後まで動かし、うまくいってから残りを作る。
- 作業中の途中経過は1〜2行で伝える。ツールの呼び出し内容・ログ・試行錯誤の細かい経緯は書かない（初心者には情報が多すぎるため）。
- 案内文で URL を書くときは、すぐ後ろに文字やかっこを続けず、1行に単独で書く（続けると、後ろの文章までリンクになってしまうため）。

用語：MCP の「テスト設定」（`list_test_settings` で出てくるもの）は、MagicPod の画面では「一括実行設定」として表示される。ユーザーへの案内では画面の呼び方を使う。

## ステップ 0: MagicPod MCP Server の確認

`list_organizations` などの MagicPod MCP のツールが使えるか確認する。使えない場合は、作業を止めて次を案内する（API トークンをチャットに貼ってもらったり、ファイルに書いたりしない）。

```
MagicPod MCP Server が接続されていないようです。
お使いの AI ツールごとのセットアップ手順はこちらです：
https://support.magic-pod.com/hc/articles/62605396709273

設定後、AI ツールを再起動して新しいセッションでもう一度お試しください。
```

## ステップ 1: 対象のヒアリングと現状の確認

最初の依頼に書かれていることは聞き直さない。足りない項目だけ聞く。

1. **テスト対象**：URL（ブラウザ）またはアプリ名（モバイル）
2. **MagicPod の組織・プロジェクト**：指定がなければ `list_organizations` → `list_projects` で候補を出し、選んでもらう。1つしかなければそれを使う。
3. **確かめたいこと**：「これが壊れていたら困る」という機能（例：ログインして一覧が見られる、検索できる、カートに入れられる）。決まっていなければステップ2で提案する。
4. **ログインに使うアカウント**：ログインが必要なら、どのアカウントを使うか。
   - パスワードなどの秘密情報は、チャットで受け取らず、ステップにも直接書かない。この時点で、ユーザーに**シークレット共有変数**として登録してもらい、変数名を教えてもらう（ステップでは `${変数名}` で参照する）。
     - 登録場所：一括実行設定ダイアログの「詳細設定」タブで共有変数を追加し、鍵マークを押してシークレットにする（ログ上でマスクされる）
     - 参考：
       https://support.magic-pod.com/hc/articles/4408887437337
     - ユーザー ID など秘密でない値も、共有変数にしておくと複数のテストで使い回せる。
   - 練習サイトなどが公開しているデモ用アカウントは秘密ではないので、ユーザーの了承があればそのままステップに書いてよい。
5. **ソースコードの場所**（任意）：リポジトリやローカルのパスが分かれば、ロケータや期待値の精度が上がる。

あわせて、MagicPod 側の現状をツールで調べる（ユーザーには聞かない）：
- `list_test_settings`（`include_private: true`）：テスト設定（実行環境・ブラウザ／端末・アプリ）。実行できる設定がなければ、MagicPod の画面で作るよう案内する。
  - モバイルアプリ：ユーザーが設定を指定していなければ、アプリが指定されている設定を一覧にして伝え、どれを使うか選んでもらう。
    - アプリが指定されている設定：`app_type` が `app_file` で `app_file_number` が1以上、`app_url` で URL が入っている、または `installed` でパッケージ名／バンドル ID が入っているもの。`app_file_number: -1` はアプリファイルが選ばれていない。
    - 伝える内容：設定番号・設定名・実行環境（クラウド／ローカル PC など）・OS・端末・アプリの指定方法。
    - 該当する設定がなければ、作業を止めて、MagicPod の画面で作ってもらうよう案内する（MCP からは作れない）：アプリファイルをアップロード → 一括実行設定を作成し、実行環境・端末とアップロードしたアプリを選ぶ → できたら設定名を教えてもらう。
  - ブラウザの URL はステップ（「URL を開く」）にそのまま書く。設定のベース URL（`${BASE_URL}`）は使わない（使うとユーザーに画面で設定を変えてもらう必要があり、その場で作業が止まってしまうため）。
- `list_test_cases`：既にあるテストケース。スモークテストと重なるものがあれば、作らずに流用を提案する。
- `search_shared_steps`（例：「ログイン」）：ログインなどの共有ステップがあれば再利用する。

## ステップ 2: シナリオの設計と提案

### 情報の集め方

- **ソースコードがある場合**：ルーティング（画面一覧）、主要な操作の UI 要素（`id`・`data-testid`・`aria-label`・`name` など）、バリデーション・エラーメッセージ、既存の E2E テスト・fixture を確認する。
- **ソースコードがない場合**：ブラウザなら、対象ページの HTML・JavaScript（初期データ、画面の切り替え、入力の必須項目、フォーム収集などのスクリプト）を読めることがあるので先に確認する。それも難しければ、ステップ3で実際の画面を取り込みながら確かめる前提で、画面の流れだけ先に決める。
- **モバイルアプリでどんなアプリか分からない場合**：1本目の「アプリ起動」テストだけ先に作り（ステップ3の1〜6）、最初の画面を取り込んで見てから、残りの案を出す。
- **表示言語**：言語によって表示を切り替えるサイト・アプリは、テスト設定の端末の言語で表示される言語が決まる。手元のブラウザで見た言語と違うことがあるので、文言を使うステップは、取り込んだ実際の表示を見てから書く。

### スモークテストの原則

- アプリの**核心機能**だけを確かめる（網羅しない）。目安は2〜4本。
- 1本で確かめることは1つの流れに絞る。ステップ数に決まりはない（商用アプリでは画面が多く、長くなることもある）。
- ログインだけを確かめるテストは作らない。ログインはコアの操作のテストの最初で行う（その操作が通れば、ログインできることも確かめられるため）。
- 各テストは単独で実行できるようにする（前のテストの結果に頼らない）。
- 各テストの最後に、成功したと分かる確認（表示テキスト・画面の要素）を必ず入れる。
- 外部サイトを表示する画面（アプリ内の WebView など）や、金額・おすすめ・カルーセルなど中身がよく変わる部分は、文言や値までは確かめず、「その画面・枠・見出しが出ること」までにする。
- Cookie の同意バナーなどは、操作の邪魔にならなければ押さずにそのままにする（同意ボタンを押すと、テストの中で同意したことになるため）。邪魔になる場合だけ、閉じる手順を入れることをユーザーに確認する。

外部への影響：
- 決済・メール送信・データ削除など、実行すると外部に影響が出る操作は入れない。入れる場合は検証環境であることを確認する。
- 本番のフォーム（問い合わせ・資料請求など）は、最後の送信ボタンを押さなくても、確認画面に進むだけでデータが外に出ることがある。ページにフォーム収集の仕組み（マーケティングツールのスクリプトなど）が入っていると、入力内容が送られて記録されることがある。フォームを含むテストを作る前に、ページのスクリプトを確かめてユーザーに伝え、どこまで進めるか決めてもらう。作る場合は、テストだと分かる値（例：`example.com` のメールアドレス）だけを使い、毎日の一括実行の対象からは外す。

### 典型的な構成

テスト1は、ほかのテストの土台になる一番シンプルなもの（ログインなし）にする（端末の起動・画面の取り込み・実行が通るかを最初に確かめるため）。

```
テスト1: 主要な画面が表示される
  - ブラウザ：対象 URL を開く / モバイル：アプリを起動する（テストの最初に自動で起動される）
  - 最初の画面の主要な要素（ヘッダー、メインの一覧、ボタンなど）が表示されていることを確認
  - ログインなしで行ける範囲で、メニュー・タブから主要な画面に移動し、各画面の要素を確認

テスト2: コアの操作ができる
  - ログインが必要なら、ステップ1で決めたアカウントでログイン（共有ステップがあれば使う）
  - 検索・登録・カート追加など、そのアプリの中心となる操作
  - 結果が反映されていることを確認

（コアの操作が複数あれば、テスト3以降に1つずつ分ける）
```

### 画像差分チェックの決め方

- 画像差分チェック（`assert_no_visual_diff`）は、要素ごとの確認では気づけないレイアウト崩れを見つけるためのもの。シナリオ案の段階で、入れるかどうかを決める。聞くのはこの1回だけにし、テストケースを作るたびには聞かない。
- 入れるのは **1テストに1つ、主要な画面にだけ**（1本目の最初の画面の確認のあとなど）。多く入れると差分の確認が大変になり、中身を見ずに承認するようになってしまうため。
- 中身がよく変わる画面（カルーセル・金額・日付・アニメーション・広告・Cookie バナーなどが大きく写る画面）には入れない。入れたい場合は、MagicPod の画面で除外領域を指定してもらう必要があることを伝える。
- 提案の表に「入れる（おすすめ）」「なし」を書いて、おすすめを決めた形で見せる。下の提案の形にある「画像差分チェックについて」の説明は、その会話で初めて出すときだけ付ける。
- 最初の依頼で「画像差分はいらない」「入れて」と言われていれば、それに従い、聞かない。
- 参考：
  https://support.magic-pod.com/hc/articles/4408918323225

### 提案の出し方

次の形で見せて、了承をもらってから作成に進む。

```
## スモークテスト案（MagicPod プロジェクト：<組織>/<プロジェクト>）

| # | テスト名 | 確かめること | 画像差分チェック |
|---|---------|-------------|----------------|
| 1 | [Smoke] 主要な画面の表示 | ... | 入れる（おすすめ） |
| 2 | [Smoke] <コアの操作> | ログインして〇〇できる | なし |

作成先：テストケースフォルダ「スモークテスト」（なければ作成）
実行に使う一括実行設定：<設定名>

まず #1 を作って動作確認し、うまくいったら #2 以降を作ります。

画像差分チェックについて
・画面全体の見た目が前回と変わっていないかを、画像で比べる確認です。レイアウト崩れなど、ボタンや文字の確認だけでは気づけない問題を見つけられます。
・最初の実行のあと、MagicPod の画面で基準にする画像を「承認」する作業が1回だけ必要です。
```

## ステップ 3: MagicPod でテストケースを作成

了承が取れたら、1本ずつ次の流れで作る。

**最初の1本（テスト1）を作り終えて、最初から通しで動作確認が通るまで、2本目に進まない。** 1本目が通ったら、1〜2行で伝えてから残りを作る。1本目で解決できない問題（設定・端末・ログインなど）が出たら、そこで止めてユーザーに相談する。

1. **フォルダを用意**：`manage_test_cases`（`action: create_folder`、`folder_name`）で「スモークテスト」フォルダを作る（既にあれば流用）。1つのプロジェクトで複数のサイト・アプリを扱っている場合は、`parent_folder_number` を指定して、サイトごとのサブフォルダに分ける。
2. **空のテストケースを作成**：`manage_test_cases`（`action: create_test_case`、`test_case_name`、`folder_number`）。テスト名は `[Smoke] ...` で揃える。
3. **説明と起動モードを設定**：作成時には説明を付けられないので、続けて `manage_test_cases`（`action: update_test_case`）で `description` と `test_start_mode` を設定する。`start_session` の**前に**行う（後で変えると、次の `edit_steps` が「ほかのユーザーが変更した」で失敗する。その場合は `read_test_case`（`force_refresh: true`）で読み直してから続ける）。
   - **説明は全テストケースに必ず付ける。** あとから見た人が、テストを開かなくても何のテストか分かるようにするため。1〜2文で、次を書く。
     - 何を確かめるテストか（例：「〇〇すると、△△が表示されることを確かめる」）
     - 前提や注意があれば（使うアカウント・データ、外部への影響がないこと、データが元に戻るか、画像差分チェックを入れていることなど）
   - **起動モード**：各テストが単独で動くよう、前のテストの状態（ログイン・Cookie・アプリのデータ）を引き継がないモードにする。
     - ブラウザ：`with_clearing_app_info`（初回のみプロセス再起動＋Cookie クリア）にする。初期値の「初回のみプロセス再起動」だと Cookie が残り、一括実行で前のテストのログイン状態を引き継いで失敗する。
     - モバイルアプリ：`with_clearing_app_info`（プロセス再起動＋アプリデータのクリア）を基本にする。ログイン状態などを残したい事情があれば、ユーザーに確認する。
4. **セッション開始**：`start_session` に作成したテストケース番号を渡す。返ってくるガイダンス（ツールの使い方・コマンドの書き方・共有ステップ一覧）に従う。
5. **端末を起動**：`manage_device`（`start`、ステップ1で決めた設定番号）。端末はセッション（テストケース）ごとに起動する。途中で端末が止まったり、タイムアウトしたりしたら、もう一度 `start` する。
6. **画面を取り込む**：ブラウザは最初のステップ（URL を開く）を書いて実行してから、モバイルは端末を起動するとアプリが立ち上がるのでそのまま、`capture_ui` で取り込む。同じ画面を何度も取り込まず、既存の UI は `inspect_ui` で再利用する。
7. **ステップを書く**：使うコマンドは先に `get_command_definition` で定義を確認し、`edit_steps` で追加する。
   - **UI 要素の名前**：自動の名前（`area(3)` など）や画面上の値（メールアドレスなど）のときは、先に `edit_ui_elements` で分かりやすい名前に変える。
   - **ロケータ**：自動で付くロケータは、画面に表示されている値（金額・名前などのデータ）に頼ったものになりやすい。データが変わると壊れるうえ、その値を確かめるステップでは確認の意味がなくなる。見出しや項目名、行・列の位置など、画面の構造で指すロケータに `edit_ui_elements`（`add_locator`、既存のロケータは置き換わる）で変える。自動のロケータで要素が見つからないときは、取り込んだ画面で要素の実際の属性（id・resource-id・テキストなど）を確かめ、その値で指すロケータに直す。不安なときは `inspect_locators` で候補を出して検証する。
   - **コメント**：使う人は初心者が多いので、テストの中身を読んで分かるようにする。`comment` コマンドで、次の2種類だけを入れる。1ステップごとには付けない（ステップ自体が読める形で表示されるので、多すぎるとかえって読みにくく、直すのも大変になる）。
     - **まとまりの見出し**：操作のまとまりの先頭に、何をしている部分かを1行で（例：「ログインする」「商品をカートに入れる」「結果を確かめる」）。
     - **分かりにくいところの理由**：初心者が見て「なぜ？」となる箇所にだけ（例：待ちを入れている理由、条件分岐の意味、公開のデモ用アカウントをそのまま書いている理由、変わりやすい中身までは確かめない理由、ロケータを直した理由）。
     - 例（商品をカートに入れるテスト）：
       ```
       # ログインする
         メールアドレス・パスワードを入力 → ログインをタップ
       # 商品をカートに入れる
         商品一覧の1件目をタップ → カートに入れるをタップ
       # 結果を確かめる
         カートの件数が「1」であることを確認
       ```
   - **画像差分チェックを入れる場合**：確かめたい画面の確認ステップのあとに `assert_no_visual_diff` を1つ入れ、コメントで「この画面の見た目が前回と変わっていないかを画像で比べる（最初の実行のあとに基準の画像を承認する）」と書く。
     - パラメータ：`name` に何の画面か分かる名前を付け、`setting` は新しく作るとき `{"baseline_id": null, "supplemental_update_id": "<ほかと重ならない文字列>"}` にする（保存すると `baseline_id` が割り当てられる）。
     - 最初の実行では期待値画像がまだないので、結果は「要確認」になる。これは失敗ではないので、ほかの確認ステップが通っていれば動作確認はできたとみなす。
     - 期待値画像の承認・除外領域・許容不一致率の設定は MCP からはできないので、報告でユーザーに承認をお願いする（ステップ5）。
8. **動作確認**：書き足した部分は `start_ref` を付けて途中から実行し、1本できたら**最初から通しで**実行する（起動モードの問題は通しで実行しないと分からない）。
   - 結果は `execute_partial_steps` の戻り値だけで判断せず、`get_test_run`（`result`）のステータスも見る（画像差分チェックの「要確認」は、戻り値では「succeeded」になることがある。`get_test_run` では `unresolved` になる）。
   - 失敗したら `get_test_run`（`result`、`log_search`）で原因を見て直す。同じ修正を3回試してだめなら、そこで止めてユーザーに相談する。
9. **後片付け**：1本できるごとに `manage_device`（`terminate`）で端末を止めてから、次のテストに進む（クラウド端末の場合）。
10. **最後の確認**：全部できたら、`list_test_cases` で、作ったテストケース全部に説明が付いているかを確かめる。

注意：
- テストケースはプロジェクトのデフォルトブランチに作られる。ブランチを分けて作りたい場合は、先にユーザーに確認する。

## ステップ 4: 一括実行（任意）

ユーザーが希望したら、`execute_batch_run`（`mode: start`）で一括実行し、`list_batch_run_test_runs` で結果を確認する。

- ローカル PC の設定では、一括実行はユーザーの PC 上の MagicPod Desktop で動く。`execute_batch_run` が起動用のリンクを返した場合は、それをユーザーに渡して開いてもらう（MagicPod Desktop が起動して実行される）。
- 一括実行設定によっては、スモークテスト以外のプロジェクト内の全テストが実行対象になっている。実行前に対象を確認し、スモークテストだけを流したい場合は、ステップ5の「毎日自動で実行する設定」の手順で、実行対象を絞ってもらう（MCP からは設定できない）。

## ステップ 5: 結果の報告

報告は短くする。**「やっていただくこと」（必要な作業）と「さらに活用するには」（やりたければでよいもの）をはっきり分けて**書く（初心者は、どれが必須でどれが任意か区別しにくいため）。

- 作業の経緯・参照したファイル・ツールの詳細は書かない。案から変えたところがあれば1行だけ書く。
- 「やっていただくこと」には、その人に当てはまるものだけを番号付きで書く。項目ごとの説明は短くし、詳しい手順はヘルプのリンクに任せる。
- 「さらに活用するには」は2項目までにする。

```
## 作成したスモークテスト

| # | テスト名 | 動作確認 | URL |
|---|---------|---------|-----|

| 2 | [Smoke] <コアの操作> | ✅ 成功 | <URL> |

作成先：<組織>/<プロジェクト>（フォルダ「<作ったフォルダ名>」）

   次の実行結果を開き、画像差分のメッセージ → 問題なければ「承認」を押してください。
   <実行結果の URL>
```

### 毎日自動で実行する設定（「やっていただくこと」に必ず入れる）

スモークテストは、作って終わりではなく毎日回して、アプリが壊れていないかを毎日確かめるのが大事。MCP からは設定できないので、ユーザーに設定してもらう。使った一括実行設定の名前と、作ったフォルダ名（またはテストケース番号）を当てはめて、実行環境に合うほうだけを書く。

**クラウド・外部クラウド（BrowserStack など）の場合**

```
MagicPod の画面で設定します。
1. 「テスト一括実行」タブで「<一括実行設定名>」の「詳細」を開く
2. 「実行対象」タブで、フォルダ「<作ったフォルダ名>」だけにチェックを入れる（プロジェクトの全テストを回したい場合は不要）
3. 右上の「︙」→「編集」で「共有」にする（スケジュールを組むのに必要です）
4. 「一括実行をスケジュール」で時刻と曜日を設定する
5. 「共通設定」で、結果のメール通知か Slack 通知をオンにする
画像差分チェックを入れたテストは、承認するまで結果が「要確認」になるので、先に承認を済ませてください。
実行対象の絞り方：
https://support.magic-pod.com/hc/articles/6760000467481
通知の設定：
https://support.magic-pod.com/hc/articles/7573429938073
```

**ローカル PC（MagicPod Desktop）の場合**

テストはユーザーの PC 上で動くので、画面のスケジュールは使えない。PC で「コマンドライン一括実行」を動かし、それを CI ツールや PC のスケジュール機能で毎日起動してもらう。

```
ローカル PC の設定では、テストはお使いの PC 上で動きます。毎日回すには、PC で「コマンドライン一括実行」を動かし、それを CI ツール（Jenkins など）や PC のスケジュール機能で毎日起動します。
1. 「テスト一括実行」タブで「<一括実行設定名>」の「詳細」を開き、「実行対象」タブでフォルダ「<作ったフォルダ名>」だけを対象にする
2. 次の記事の手順で、コマンドで一括実行できることを確かめる
   https://support.magic-pod.com/hc/articles/6468420020633
3. そのコマンドを、CI ツールや PC のスケジュール機能（Windows のタスクスケジューラ、Mac の cron など）に登録する
```

ユーザーから詳しい手順を聞かれたら、次を補足する：
- 準備として、MagicPod Desktop を一度起動してログインし、終了しておく（起動したままだとコマンドライン実行が失敗する）。
- 設定ファイル（magic_pod_config.json）に、組織名・プロジェクト名（画面の URL に出ている英字の名前）と一括実行設定の番号を書く。
- 決まった時刻に PC がスリープしていないこと、モバイルなら端末やシミュレーターが使える状態であることを確かめる。
- Jenkins で毎日実行する例：
  https://support.magic-pod.com/hc/articles/4409927139993

そのほか：
- 外部に影響が出るおそれがあるテスト（本番のフォームに入力するテストなど）は、毎日回す対象から外す。フォルダで絞るならそのテストを別のフォルダに移すか、テストケース番号の指定で除くよう案内する。
- 毎日回す一括実行設定がほかのテストと共用で、実行対象を変えると困りそうな場合は、スモークテスト用に設定を1つ追加してもらう（「︙」→「新しい設定を追加」）。
- モバイルアプリでアプリのビルドを差し替えながら回したい場合は、「さらに活用するには」に、CI サービスから MagicPod Web API でアプリのアップロードと一括実行を行う方法を入れる。
  https://support.magic-pod.com/hc/articles/28166577781401

## うまくいかないとき

- **MCP のツールがエラーになる**：エラー内容をそのまま伝える。同じ呼び出しを繰り返さず、3回試してだめなら止める。
- **端末が起動しない**（`manage_device` が失敗する）：3回試してだめなら止める。設定（アプリファイル・OS バージョン・端末）の問題のことがあるので、MagicPod の画面でその設定を使って既存のテストを1本実行できるか確かめてもらうか、別の設定を使うか、ユーザーに相談する。
- **認証エラー**：MagicPod への再ログインを案内する（ステップ0のセットアップ手順の記事を参照）。
- **対象 URL にアクセスできない**：URL の誤り、または VPN・社内環境の可能性。社内環境なら MagicPod Desktop（ローカル PC 実行）の利用を案内する。
- **ソースコードが見られない**：`capture_ui` で取り込んだ実際の画面から UI 要素を確かめる。それでも分からない要素は、ユーザーに聞く。
- **詳しい使い方の質問**：`find_help_center_article` で MagicPod ヘルプセンターを検索し、記事のリンクを添えて答える。
