# Flakyの原因の型と直し方

履歴とログから「どの型か」を見分け、型に合った直し方を選ぶ。どれも出発点で、決めつけではない。複数の失敗を読み比べ、共通点で判断する。

## 目次
1. 表示・読み込みの遅れ(タイミング)
2. すぐ消える要素(タイミング)
3. 日付・曜日で変わる画面(テストデータ・日付)
4. テストデータの状態・テストの順序
5. 実行基盤の一時的な問題
6. Flakyに見えるが、Flakyではないもの
7. やってはいけない直し方

---

## 1. 表示・読み込みの遅れ

**見分け方**
- 失敗は毎回、画面の読み込み直後の確認・操作のステップ(「◯◯が表示されている」「◯◯をクリック」など)。
- エラーは「UI要素が存在しません」「要素が見つかりません」。失敗時の画面は「読み込み中」や空の一覧。
- ログでは、そのステップの開始から失敗まで数十秒止まっている。要素が見つからないと自動修復を試みるが、「類似度が低い」などで修復できずに終わることが多い。
- 成功した実行の同じステップは数秒以内。まれに長くかかっても待ち切って成功している回がある(遅れの幅が広い)。
- 同じ画面を通る別のテストケースも、たまたま遅い回に当たれば同じ形で失敗する。どのテストが失敗するかは、その回の運次第。
- ブラウザのテストなら、`browser_log`(ログの名前は例)で、その時刻のAPIの遅延やエラーが見えることがある。遅れの原因がアプリ側にある裏付けになる。

**直し方**
- 確認・操作の直前に、`wait_visible`(UI要素が表示されるまで待つ)を入れ、`limit`(秒)を、履歴で見た最も長い遅れより余裕のある値にする。対象は、読み込みが終わったことを示す要素(一覧の最初の項目など)。
- 「読み込み中」の表示がある画面なら、`wait_invisible` で読み込み表示が消えるのを待つ方法もある。
- 同じ画面を通るほかのテストケースにも、同じ待ちを入れるか検討する。ログイン直後のように多くのテストケースが通る場所なら、共有ステップに入れると効率がよい(共有ステップの変更はブランチではできない点に注意)。
- 遅れが数十秒に及ぶなら、アプリ側の性能の問題として開発者に確認することも「やること」に入れる。

## 2. すぐ消える要素

**見分け方**
- 通知(トースト)・メッセージなど、数秒で消える要素の文言の確認で失敗する。
- エラーに出るロケーターが、確認したい要素とは別の要素のものになっていることがある(本来のロケーターで見つからず、別のロケーターが使われた)。
- 失敗時の画面に、その要素がもう無い。
- 直前のステップが遅かった回(自動修復が動いた、など)で失敗しやすい。アプリ側で表示時間がばらつく作りのこともある。

**直し方**
- 操作の直後に確認する順番になっているかを見る。間に別の操作があれば、確認を先に移す。
- `wait_equals_value` / `wait_contains_value` で、表示を待ってから確認する(消える前に捕まえる)。
- それでも不安定なら、消えない表示(カートの件数、一覧の内容など)で同じことを確かめる方法に変える。その場合は、確かめる対象が変わることを報告に書く。

## 3. 日付・曜日で変わる画面

**見分け方**
- 失敗が特定の曜日(土日など)・日付(月末、祝日)・時刻だけに集まる。失敗した実行の日時を、曜日つきで並べると分かる。
- 失敗の形は、入力・選択の不足によるエラー(「◯◯を選択してください」)、確認画面に進めない、表示される日付・金額の不一致など。
- テストケースの説明欄やアプリの画面に、日付から計算される項目(配送日、期限、予約日など)がある。
- 画面の初期値(デフォルトで選ばれている値)が、日によって変わったり空になったりする。

**直し方**
- 画面の初期値に頼らず、テストで値を明示的に選ぶ・入力するステップを足す(`select`、`input`)。
- `select`(プルダウンから選ぶ)は、**選択肢の表示テキスト(`text_value`)で選ぶ**コマンドで、「何番目」の指定は無い。選択肢の文言が日によって変わるときは、次のどちらかで、選ぶ文言を変数に作ってから `select` に `${変数名}` で渡す。
  - **画面の選択肢から文言を取る(おすすめ)**: 選びたい選択肢(例: 空でない最初の選択肢)を指すUI要素を用意し、`store_value_to_variable` でその文言を変数に入れる。ロケーターの例: `xpath=//select[@id='delivery-date']/option[@value!=''][1]`。UI要素が無ければ、了承後の適用時に `edit_ui_elements` で既存のUIにロケーターを足す。画面の表示形式に左右されないので壊れにくい。
  - **日付を計算して作る**: `date_calculation` で、たとえば2日後の日付を、表示形式に合わせた書式で変数に入れる(`date_type` に `MPD-DATE-FNS-FORMAT`、`date_format` に `M/d(E)`、`language` に `ja` など。曜日の表記が画面と一致するかは確かめる)。選択肢の範囲(何日後から何日後まで)の外にならないよう注意する。
- どちらの方法も、修正案を出す前に `get_command_definition` でパラメーターを確かめる。
- 日付に依存する確認(「配送日が◯日」など)を足すときは、上と同じく計算した値と比べる。
- この型は、条件の日(週末など)にならないと再現しない。ブランチでの確認は、条件の日に実行するか、条件を満たす日付を選ぶ形にして確かめる、と報告に書く。

## 4. テストデータの状態・テストの順序

**見分け方**
- 前のテストケースが残したデータ(カートの中身、ログイン状態、登録済みのデータ)で結果が変わる。一括実行の中の順番や、前のテストが失敗したかどうかと連動する。
- 同じデータ(ユーザー名、メールアドレスなど)を毎回登録して、「既に登録されています」で失敗する。

**直し方**
- テストの最初に、前提の状態を作る・消すステップを足す(カートを空にする、ローカルストレージを消す、など)。テスト設定の「ブラウザの開始方法」も確認する。
- 毎回登録する値には、`store_current_second_based_unique_value_to_variable` などで一意な値を使う。

## 5. 実行基盤の一時的な問題

**見分け方**
- 失敗のステップやエラーがばらばらで、アプリと関係のないエラー(ブラウザの起動失敗、通信エラーなど)が出る。
- 同じ時間帯に、複数のテストケースが関係なく失敗している。
- `test_engine_log` にセッション切れ・接続エラー、`device_log` に端末の再起動やメモリ不足などが出ている(ログの名前は例。その時点で指定できる値を確かめる)。
- `crash_log` にアプリのクラッシュがあれば、実行基盤ではなくアプリの不具合を疑う(6を参照)。

**直し方**
- テストケースの修正では直らない。再実行で再現するかを見て、続くようならMagicPodのサポートに問い合わせる、と書く。

## 6. Flakyに見えるが、Flakyではないもの

- **ある設定でだけ毎回失敗**(狭い画面でメニューが隠れる、など): 環境起因。手順を設定ごとに分岐させるなどの直し方になる。Flakyとしては扱わない。
- **ある時点から毎回失敗し、元に戻すと成功**: アプリやテストの変更によるもの。magicpod-failure-investigation スキルで、原因になった変更を調べる。
- **アプリのクラッシュ**(`crash_log` などに記録がある): たまにしか起きなくても、アプリの不具合。テストの修正ではなく、開発者への確認を「やること」に入れる。
- **1回だけの失敗**: 判断材料が足りない。ログで型が分かれば「様子見」として挙げ、履歴が溜まってから見直す。

## 7. やってはいけない直し方

- 確認のステップを消して「通るようにする」。
- 固定時間の待機を長く入れて、遅れを吸収する(遅いときには足りず、毎回の実行が遅くなる)。
- 失敗を無視する設定にする、再実行で成功すればよしとする、実行中の失敗テストのリトライの回数を増やして失敗を隠す(原因が残ったままになる)。
- 原因を特定しないまま、複数の箇所を同時に変える(どれが効いたか分からなくなる)。
