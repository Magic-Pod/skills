# magicpod-flaky-test-fix

MagicPodの実行履歴から不安定なテストを見つけ、原因と直し方を示すスキル。

「たまに落ちるテスト」は、放っておくと「どうせまたFlakyだろう」と失敗が無視されるようになり、本物の不具合を見逃す原因になる。一方で、待ち時間を闇雲に延ばしたり、確認のステップを消したりして「とにかく通るようにする」と、テストが何も確かめなくなる。このスキルの目的は、**履歴を根拠に原因を特定し、テストが確かめるべきことを保ったまま安定させる修正**を提案すること。

## 前提と守ること

- **調べるのと提案するのは自由に行ってよい。書き込みは、ユーザーが修正案を見て了承してから。** 了承は修正ごとに取る。了承の前に、ブランチの作成・テストケースの編集・バッチ実行の開始をしてはいけない。
- **修正はMagicPodのブランチ上で行い、デフォルトブランチ(main)は直接変えない。** mainへの反映(マージ)は、ユーザーがMagicPodの画面で行う。
- MagicPod MCPの次のツールを使う。読み取りは `start_session` 不要。
  - 読み取り: `list_batch_runs`、`list_batch_run_test_runs`、`list_test_runs`、`get_test_run`、`get_test_case_detail`、`list_test_settings`
  - 修正案の確認(読み取りのみ): `start_session`、`get_command_definition`。セッションを開いてコマンドの定義を読むだけで、テストケースは変わらない。
  - 修正(了承後のみ): `manage_branch`(ブランチ作成)、`start_session`(`branch_name` を指定)、`read_test_case`、`edit_steps`、`edit_ui_elements`、`execute_batch_run`(`branch_name` を指定)
- 共有ステップの変更・テストケースの説明欄の変更・UIの削除は、ブランチでは行えない。修正にそれが必要なら、そのことをユーザーに伝え、どうするか決めてもらう。
- GitHubなどでアプリのコードが読めるなら、原因の裏付けに使ってよい(読み取りのみ)。読めなければ、履歴とログだけで判断し、そのことを報告に書く。

## 調べる量の目安

調査は、修正案の根拠になる分だけにとどめる。読むものが増えるほど時間がかかり、報告も長くなる。

- **ユーザーがテストケースを指定したら、そのテストケースの `list_test_runs` から始める。** プロジェクト全体のバッチ実行を集めるのは、テストケースの指定が無いときだけ。
- **履歴は期間に見合う件数だけ取る。** `list_test_runs` や `list_batch_runs` の `count` は、目安の期間に足りる数(例: 30)にする。
- **`get_test_run` の `result` を取るのは、原因ごとに1回だけ。** `result` には失敗時のスクリーンショットと画面のUI要素一覧が付いてきて大きい。この1回で画面の様子をつかんだら、ほかは次のログ検索で足りる。
- **ログは全文を読まず、`log_search` で必要な行だけを取る。**
  - 詳しく読む1回: ステップの開始行・エラー・自動修復の行を取る(パターンの例: `\[[0-9.]+\] |Error|修復|healing`)。ステップごとの時刻も、この行から分かる。
  - ほかの失敗の確認: エラーと自動修復の行だけを取る(例: `Error|修復|healing`)。同じステップ・同じエラーなら、それ以上は開かない。
  - 上の `test_run_log` で原因の型が決まらないときだけ、ほかのログも `log_type` を切り替えて `log_search` で読む(手順3を参照)。
- **スクリーンショットは追加で取らない。** `result` に付いてくる失敗時の画面で足りないときだけ、`screenshots` で取る。
- **成功した回の速さは、`list_test_runs` の開始・終了時刻で比べる。** 成功した回のログは開かない。
- **集計から外す実行は読まない。** 開発中の手動実行など、一覧の時点で除くと決めたものは、中身を開かない。
- **Flakyではないもの(毎回失敗、変更による失敗)は、表に載せるだけで深追いしない。** 原因が一目で分かれば一言添える。期間中ずっと成功しているテストの潜在的なリスクも探さない。
- **アプリのコードは、修正案を決めるのに必要なときだけ、2〜3回の呼び出しで読み終える。** リポジトリ名をユーザーが示していれば、探さずにそれを使う。ファイル一覧を1回取り(`gh api "repos/<owner>/<repo>/git/trees/HEAD?recursive=1"` のように、URLは引用符で囲む)、関係するファイルを1〜2個だけ読む。
- 開発中の手動実行など、履歴のノイズになりそうな実行が多い期間は、定期実行を中心に数える。

## 手順

### 1. 履歴を集める

ユーザーがテストケースを指定していれば、`list_test_runs` でそのテストケースの実行履歴を取り、テスト設定ごとに分ける。指定が無ければ、対象のプロジェクト(URLから組織名・プロジェクト名を読む)で `list_batch_runs` を使い、直近のバッチ実行を集める。期間の指定が無ければ、直近1〜2週間、または直近30回程度を目安にする。

- テスト設定(PC・モバイルなど)ごとに分けて扱う。設定が違えば、同じテストケースでも別物として数える。
- 失敗したバッチ実行は `list_batch_run_test_runs` で中身を見て、どのテストケースが失敗したかを控える。成功したバッチ実行は全件成功なので、中身を見なくてよい。
- 手動で一時的にアプリを変えていた時間帯など、ユーザーから「この期間は除いて」と言われたら除く。

集めた結果を、テストケース×テスト設定ごとに「実行回数・失敗回数・失敗した実行の日時(曜日も)」の表にまとめる。

### 2. 不安定なテストを見分ける

表を、次の形に当てはめる。

| 履歴の形 | 判断 | このスキルで扱うか |
|---|---|---|
| ある設定で、成功と失敗が不規則に混ざる | Flakyの候補 | 扱う |
| 特定の曜日・日付・時刻だけ失敗する | 日付・テストデータ起因の候補 | 扱う |
| ある設定では毎回失敗し、別の設定では毎回成功する | 環境起因。Flakyではない | 扱わない(報告に一言書く) |
| ある時点から毎回失敗し、元に戻ると成功する | アプリやテストの変更によるもの。Flakyではない | 扱わない(magicpod-failure-investigation を勧める) |
| 期間中ずっと成功 | 安定 | 扱わない |

毎回失敗するテストをFlakyと呼ばないこと。毎回失敗するものは原因がはっきりしているので、別の直し方(手順の分岐、仕様変更への追従)になる。

1回だけの失敗は、それだけでFlakyとは決めない。ログを見て、待ちや表示に関係する失敗なら「候補(様子見)」として挙げる。

### 3. 失敗した実行を読む

候補ごとに、失敗した実行を1回 `get_test_run` で詳しく読む(`result` と、`log_search` でステップの開始行・エラー・自動修復の行)。ほかの失敗は `log_search` でエラーの行だけを取り、同じステップ・同じエラーかを確かめる(「調べる量の目安」を参照)。

- **毎回同じステップで、同じエラーか。** 同じなら原因は1つの可能性が高い。
- **失敗したステップまでにかかった時間。** 成功した実行の同じステップと比べる。失敗時だけ長く止まっていれば、表示や読み込みの遅れ。
- **失敗時の画面。** 「読み込み中」のまま、要素が出る前、通知が消えた後、などを見る。
- **失敗した日時の曜日・日付。** 週末だけ、月末だけ、などの偏りがあれば、日付で変わる表示や入力を疑う。
- **テストケースの手順と説明欄。** 既知の不安定要素や前提が書かれていることがある(書かれていることが原因とは限らない)。
- **ほかのログ(必要なときだけ)。** `test_run_log` だけでは「表示の遅れ」か「実行基盤の問題」か「アプリのエラー」かが分からないとき、`get_test_run` の `log_search` で `log_type` を切り替えて読む。ログの種類と名前は変わることがあるので、その時点で `log_type` に指定できる値を確かめて使う。現時点の例:
  - `test_engine_log`: テストエンジン側の動き(要素探索のタイムアウト、セッション切れなど)。実行基盤の一時的な問題の見分けに使う
  - `device_log`: 端末側のログ(モバイルアプリのテスト)。アプリの例外、OSのダイアログ、メモリ不足など
  - `browser_log`: ブラウザのコンソール(ブラウザのテストのみ)。JavaScriptのエラーや、APIの遅延・4xx/5xx
  - `crash_log`: アプリのクラッシュ。記録があれば、Flakyではなくアプリの不具合として扱い、開発者への確認を「やること」に入れる

  全文は読まず、失敗したステップの時刻の前後や `Error|Exception|crash|timeout` のようなパターンで行を絞る。読むのは代表の失敗1回で足りる。

原因の型と、それぞれの見分け方・直し方は `references/flaky-patterns.md` にまとめてある。最初に必ず目を通すこと。

### 4. 修正案を作る

原因ごとに、テストケースのどのステップをどう変えるかを、変更前と変更後の手順で示す。修正案を作るときは、次を守る。

- **テストが確かめていることを減らさない。** 確認のステップを削除する、確認を緩める(「等しい」を「含む」にするなど)は、原因がそれでしか解決しない場合だけにし、理由を書く。
- **固定時間の待機(`wait_fixed_time`)より、状態を待つコマンド(`wait_visible` など、待ち時間の上限 `limit` つき)を使う。** 固定の待機は、遅いときには足りず、速いときには無駄になる。上限は、履歴で見た最も長い遅れより余裕を持たせる。
- **日付で変わるものは、テストの側で値を決める。** 画面の初期値に頼らず、選択・入力のステップを足す。日付の計算が必要なら `date_calculation` を使う。
- **アプリ側に直すべき問題がありそうなら、それも書く。** たとえば読み込みに数十秒かかるのは、テストを待たせて済む話ではなく、ユーザーにとっても問題かもしれない。テストの修正と並べて、開発者への確認を「やること」に入れる。
- **修正案に書くコマンドは、提案の前に `get_command_definition` で定義を確かめる。** 対象のテストケースで `start_session` を呼び(読み取りのみ)、そのセッションIDで、使うつもりのコマンドの定義をまとめて1回で取る。定義に無いパラメーター(たとえば、`select` で「何番目の選択肢」を指定する)は修正案に書かない。思い込みのコマンドで提案すると、了承後に適用できず、やり直しになる。
- 定義を確かめられなかったとき(セッションを開けないなど)は、そのことを「未確認事項」に書く。

### 5. 報告し、了承を求める

「報告の形式」に沿って報告する。最後に、どの修正を適用してよいかをユーザーに聞く。ここで止まり、了承が無ければ書き込みは何もしない。

### 6. 了承された修正を、ブランチで適用して確かめる

ユーザーが了承した修正だけを行う。

1. ブランチを作る(`manage_branch`、`create_branch`)。ユーザーが名前を指定しなければ、`fix-flaky-<テストケース番号>-<日付>` のような名前にする。既存のブランチを使うよう言われたらそれを使う。
2. `start_session` を `branch_name` つきで呼び、`read_test_case` でステップの `ref` を確かめる。
3. `edit_steps` で修正する。UI要素は既存のものを使う。新しいロケーターが必要なら `edit_ui_elements` で既存のUIに足すか、`capture_ui` で取る。
4. ブランチで実行して確かめる。`execute_batch_run`(`branch_name` を指定。必要ならテスト設定の「実行対象」で対象を絞ったもの)を使う。Flakyは1回の成功では直ったと言えないので、実行回数の目安とその理由をユーザーに伝えてから実行する(実行はクラウドの実行回数を使うため)。日付起因のように、すぐには再現できない条件は、「どの条件で確かめられるか」を書いて、確認を後に回してよい。
5. 結果を報告し、mainへのマージはユーザーが画面で行うよう伝える。ブランチのURLも示す。

## 報告の形式

読む人がまず知りたいのは「どのテストが不安定で、何をすればいいか」。調べた過程は後ろに短くまとめる。全体で2,000字前後(長くても3,000字)に収める。1文は短く、1つの箇条書きには1つのことだけを書く。

```markdown
# 不安定なテストの調査(<期間>)

## 結論
<どのテストが不安定で、主な原因は何で、どう直すかを3文以内で>

## やること
1. **<誰が>**: <何を、どのテストケースに>
2. ...

## テストケースごとの安定性
| テストケース | テスト設定 | 失敗 / 実行 | 判断 | 原因(ひとこと) |
|---|---|---|---|---|

## 修正案
### <テストケース名>: <原因をひとことで>(信頼度: 高/中/低)
- 根拠: <失敗の共通点、時間・曜日の偏り、画面の所見を2〜4個>
- 修正(変更前 → 変更後):
  - ステップN: <変更前の手順> → <変更後の手順>
- この修正で確かめていることは変わらない/変わる点: <一言>

## 未確認事項
<無ければ省略>

---
上の修正案のうち、適用してよいものを教えてください。了承をいただいたものだけ、MagicPodのブランチで修正し、そのブランチで実行して確かめます。
```

「判断」の列には、Flaky(タイミング)/ Flaky(テストデータ・日付)/ 環境(Flakyではない)/ 変更による失敗(Flakyではない)/ 安定 / 様子見 のいずれかを書く。安定しているテストは、表の行を省いて「ほかの◯件は期間中すべて成功」とまとめてよい。

信頼度の目安: 失敗を2回以上読み、共通点と偏りが説明でき、コードや画面でも裏付けられれば「高」。失敗が1〜2回で、ログからの推定が中心なら「中」。推測が多ければ「低」。
