# MagicPodの失敗を読むときの手がかり

`get_test_run` の結果・ログから原因を推定するときに使う。どれも「この形なら、まずこれを疑う」という出発点で、決めつけではない。他の根拠と合わせて判断すること。

## 目次
1. 自動修復が関係する失敗
2. 失敗したステップが無い失敗
3. エラーメッセージの種類と読み方
4. 時間の手がかり
5. テスト設定(環境)の手がかり
6. 履歴の形
7. ほかのログの手がかり

---

## 1. 自動修復が関係する失敗

MagicPodは、一括実行中に操作対象のUI要素が見つからないと、AIで別の候補を探して続行する(自動修復)。ヘルプ「自動修復機能とは」。

- ログに `Element is not found. Requesting new healing result..` が出る。この行の前後で数十秒かかることが多い。
- 修復が効いて最後まで通ると、結果は「要確認」になる。承認されるまで、元のUI要素は変わらない。
- 修復が起きたテストケースが後続のステップで失敗すると、修復は自動却下され、そのテストは失敗になる。
- 同じ共有UIを使う後続のテストケースは、その修復結果を使ってすぐに通る。修復が却下されると、それらのテストケースもまとめて失敗になる(下の2を参照)。
- 自動修復は「要素が見つからない」ときだけ動く。値の確認(文言・金額の一致など)が失敗しても動かない。

**読み方**: 自動修復の記録があれば、UIのID・文言・構造の変更(仕様変更)を強く疑う。修復で余計に時間がかかったせいで、後続のステップ(数秒で消える通知の確認など)が失敗することもある。その場合の根本原因は「UIの変更」で、後続の失敗は副作用。

## 2. 失敗したステップが無い失敗

`result` の `failed_lines` が空で、ログでも全ステップが通っているのに、ステータスが失敗になっている。

- まず、同じ一括実行の中で、自動修復が起きたうえで失敗した別のテストケースを探す。あれば、修復の却下に巻き込まれたもの。根本の原因はその別のテストケースの方にあり、そちらが直れば巻き込まれた側も「要確認」に戻る。
- 画面上のエラーは「自動修復を行いましたが、後続の処理で失敗したため自動却下されました」。MCPの結果には出ないことがあるので、ユーザーに画面での確認を依頼してよい。
- 上で説明がつかなければ、画像差分チェック(`settings` の `visual_diff_pattern`)など、ステップ以外の判定を疑う。MCPでは差分画像を見られないので、画面での確認を依頼する。

## 3. エラーメッセージの種類と読み方

| メッセージの例 | 意味 | まず疑うこと |
|---|---|---|
| `UI element text "A" is not equal to "B"` | 値の確認で、実際がA、期待がB | 文言・金額の変更(仕様変更か不具合か)。Aが空文字なら、要素が非表示 |
| `UI element text "" is not equal to ...` | 要素はあるがテキストが空 | 要素が非表示(狭い画面でメニューに隠れている、など) |
| `An error occurred when attempting to interact with an element outside the viewport` | 画面外・非表示の要素を操作しようとした | 画面サイズ・レイアウトの違い(環境) |
| 要素が見つからない旨のエラー(自動修復も失敗) | ロケーターに合う要素が無い | UIの変更、または表示が間に合っていない(タイミング) |

**ロケーターに注意**: エラーの末尾に出るロケーター(`id=...` や `xpath=...`)が、ステップ名から想像する要素と違うことがある。1つのUI要素に複数のロケーターがあり、本来のものが見つからなかったため別のものが使われた、という場合。たとえば「通知の文言を確認」のステップで、エラーに説明文のロケーターが出ていたら、「通知が出なかった(または消えていた)」と読む。

## 4. 時間の手がかり

ログの各行には時刻がある。ステップ間の時間を見る。

- 値の確認が失敗するまでの待ちは、およそ20秒前後。それより長く1つのステップで止まっていれば、待機・自動修復・画面外の要素の操作など、特別なことが起きている。
- 画面外の要素の操作は、失敗が確定するまで数分かかることがある。
- 同じテストケースが、成功した回と比べて特定のステップだけ極端に遅い → 表示の遅れ(Flaky(タイミング)の手がかり)。表示を待つ確認は、遅れても待ち切って成功することがあるので、「失敗していない回の遅さ」も履歴で見る価値がある。

## 5. テスト設定(環境)の手がかり

- `list_batch_run_test_runs` のパターン情報や、`get_test_run` の `settings` で、ブラウザ・端末・画面サイズ(`browser_window_size`、`device_type` が `mobile_emulation_by_chrome` など)を確認する。
- 同じテストケースが、あるテスト設定では成功、別の設定では毎回失敗 → 環境起因。画面の狭さでメニューが隠れる、などがよくある。
- 環境起因の失敗は、毎回同じように起きるので、履歴上は「安定して失敗」に見える。Flakyとは区別する。

## 6. 履歴の形

`list_test_runs` の結果を、時系列で次の形に当てはめる。

| 履歴の形 | 疑うこと |
|---|---|
| ずっと成功 → ある時点から毎回失敗 | 変更(コード・データ・環境)。その間のPR・コミットを探す |
| 成功と失敗が不規則に混ざる | Flaky(タイミング)。失敗の箇所が毎回同じか、遅延が見られるか |
| 特定の曜日・日付・時刻だけ失敗 | Flaky(テストデータ)。日付の計算や、日によって変わる表示 |
| ある設定では毎回失敗、別の設定では毎回成功 | 環境 |
| 一度だけ失敗し、前後は成功 | Flakyか、実行基盤の一時的な問題。1回では判断しない |

## 7. ほかのログの手がかり

`test_run_log` で説明がつかないときに読む。ログの名前は例で、変わることがある。`get_test_run` の `log_type` に指定できる値を、その時点で確かめる。

| ログ(現時点の例) | 何が分かるか | こう出ていたら |
|---|---|---|
| `test_engine_log` | テストエンジンの内部の動き | 要素探索のタイムアウト、セッション切れ、コマンドの内部エラー → タイミング、またはMagicPod・インフラ側 |
| `device_log` | 端末・OS側の出来事(モバイル) | アプリの例外・ANR → アプリの不具合。OSのダイアログ・メモリ不足 → 環境 |
| `browser_log`(ブラウザのテストのみ) | ブラウザのコンソール | JavaScriptのエラー、API の 4xx/5xx → アプリの不具合やテスト環境のサーバーの問題。失敗の画面が空のときに特に見る |
| `crash_log` | アプリのクラッシュ | 記録があれば、アプリの不具合を強く疑う |

- 失敗したステップの時刻の前後だけを見る。その時刻と離れたエラーは、普段から出ている無害なものであることが多い。
- 成功した回にも同じエラーが出ていないかを比べられると、根拠が強くなる。
