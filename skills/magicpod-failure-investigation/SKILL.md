# magicpod-failure-investigation

MagicPodのバッチ実行で失敗したテストについて、「なぜ失敗したのか」「誰が何をすべきか」を、根拠つきで報告するスキル。

テストの失敗には、アプリの不具合、アプリの意図的な変更にテストが追いついていないもの、タイミングやデータによる不安定さ、実行環境の違いなど、性質の違う原因が混ざっている。報告を受けた人が「開発者にバグとして渡す」「テストを直す」「様子を見る」のどれをすべきかを判断できるようにするのが、このスキルの目的。

## 前提と守ること

- **読み取りだけを行う。** テストケースやUIの編集、バッチ実行の開始・再実行、自動修復の承認・却下、GitHubへの書き込みはしない。調べるだけで、直すのは人。必要な対応は「推奨する対応」として書く。
- **MagicPod MCP** を使う。`start_session` は不要で、以下のツールを直接呼べる。
  - `list_batch_runs` / `list_batch_run_test_runs`: バッチ実行と、その中のテスト結果
  - `get_test_run`: 1件の実行の結果・ログ・スクリーンショット・実行時の設定
  - `list_test_runs`: テストケースごとの実行履歴
  - `get_test_case_detail` または `read_test_case`: テストケースの手順と説明欄
  - `find_help_center_article`: MagicPodのヘルプセンター(仕様の確認に使う)
- **GitHub** は、GitHubのMCPサーバーか `gh` CLIの使えるほうで読む。リポジトリとブランチの決め方は手順5に書いてある。どちらも使えない、またはリポジトリが決められない場合は、コード変更の調査を省き、そのことを報告に書く。
- 根拠が足りないときは、無理に結論を出さない。「判断できない」とし、何を確認すれば判断できるかを書く。

## 手順

### 1. 調べる範囲を決め、失敗の一覧を作る

バッチ実行のURL(`app.magicpod.com/{組織}/{プロジェクト}/batch-run/{番号}/`)から組織・プロジェクト・番号を読み取る。URLが無ければ `list_batch_runs` で直近の失敗したバッチ実行を探す。

**特定のテスト結果が指定されたら、それだけを調べる。** 次のような場合は、指定されたテスト結果が調査の対象で、同じバッチ実行のほかの失敗は対象外。

- URLがバッチ実行の中の1件の結果を指している(例: `.../batch-run/12/3/` のように、バッチ実行番号の後ろに番号が続く)
- テストケースの実行結果のURL(`.../{テストケース番号}/test-run/{実行番号}/`)が貼られている
- 依頼文でテストケース名・番号が指定されている(「このバッチ実行の◯◯のテストだけ見て」など)

ほかの失敗したテストケースは、分析も報告もしない。例外は、指定されたテストの失敗を説明するのに必要な場合だけ(自動修復の却下に巻き込まれた疑いがあり、修復が起きた別のテストケースを確かめる、など)。そのときも、見るのは関係する1件だけにし、報告では指定されたテストの根拠として触れる。ほかにも失敗がある場合は、「補足」に「このバッチ実行には、ほかに◯件の失敗があります(今回は調査対象外)」と1行だけ書いてよい。

範囲の指定が無く、バッチ実行全体のURLだけが示されたときは、バッチ実行の失敗をすべて調べる。

`list_batch_run_test_runs` で、失敗したテストケースと実行番号を一覧にする。テスト設定のパターン(ブラウザ・端末)が複数あれば、パターンごとに分ける。成功したテストケースも控えておく。「何が失敗したか」と同じくらい「何が成功したか」が、原因の絞り込みに効くため。

### 2. 失敗ごとに、どこで何が起きたかを見る

`get_test_run` で次を取る。

- `result`: 失敗したステップ、エラーメッセージ、失敗時の画面のUI要素
- `test_run_log`(`log_lines` で全体、または `log_search`): 各ステップの開始時刻と、途中のメッセージ
- 必要に応じて `screenshots`(失敗したステップ)、`settings`(テスト設定の中身)

`test_run_log` だけで原因が絞れないときは、ほかのログも `log_search` / `log_lines` の `log_type` を切り替えて読む。ログの種類と名前は変わることがあるので、その時点で `get_test_run` の `log_type` に指定できる値を確かめて使う。現時点の例:

- `test_engine_log`: テストエンジン側の詳しい動き。要素の探索、コマンドの内部エラー、タイムアウトの詳細など
- `device_log`: 端末側のログ(モバイルアプリのテスト)。アプリの例外、OSのダイアログ、メモリ不足など
- `browser_log`: ブラウザのコンソールのログ(ブラウザのテストのみ)。JavaScriptのエラー、通信エラー(4xx/5xx)など
- `crash_log`: アプリのクラッシュの記録。あれば「アプリの不具合」の強い根拠になる

全文は読まず、失敗したステップの時刻の前後や、`Error|Exception|FATAL|crash|timeout` のようなパターンで必要な行だけを取る。ログが空・取れない場合は、そのログは無いものとして先に進む。

読むときの勘所は `references/failure-signals.md` にまとめてある。最初の調査では必ず目を通すこと。特に次の3つは見落としやすい。

- **自動修復**: ログに「Element is not found. Requesting new healing result..」があれば、要素が見つからずAIの自動修復が動いた。UIのID・文言が変わったことを示す強い手がかり。修復が効くとそのステップは成功し、失敗は後のステップで別の形で現れる。
- **失敗したステップが無い失敗**: `failed_lines` が空で、ログでも全ステップが通っているのに失敗している場合、同じバッチ実行の別のテストケースで起きた自動修復が却下され、巻き込まれた可能性が高い。
- **紛らわしいエラーメッセージ**: エラーに出るロケーターが、そのステップで意図した要素と違うことがある(1つのUI要素に複数のロケーターがあり、別のものが使われた)。メッセージの文面だけで判断せず、ステップ名・画面・ログと突き合わせる。

### 3. 失敗をまとめる

複数のテストケースが同じ画面・同じ要素・同じ種類のエラーで失敗していれば、原因は1つの可能性が高い。原因ごとにグループにまとめ、報告もグループ単位にする。

あわせて次を比べる。

- 同じテストケースが、別のテスト設定(PCとモバイルなど)では成功しているか → 環境(画面サイズ・ブラウザ)起因の手がかり
- 失敗したテストケースに共通する手順(同じ画面を通る、同じボタンを押す)と、成功したテストケースとの違い

### 4. 実行履歴を見る

失敗したテストケースごとに `list_test_runs` で直近の実行結果を見る。

- 直前まで安定して成功し、ある時点から失敗 → 何かが変わった。その変化の時刻を「最後に成功した実行」と「最初に失敗した実行」の間に絞り込む(手順5で使う)。
- 成功と失敗が不規則に混ざる → Flakyの可能性。失敗時のエラーが毎回同じ箇所か、時間がかかっているかも見る。
- 特定の曜日・時刻・日付の近くだけ失敗 → 日付やテストデータ起因の可能性。

テストケースの説明欄に、既知の不安定要素や注意点が書かれていることがある。`get_test_case_detail` などで読み、判断の材料にする(ただし、書かれていることが今回の原因とは限らない)。

### 5. コード変更を探す(GitHubが読める場合)

#### リポジトリとブランチを決める

- 依頼文、エージェントの設定ファイル(`AGENTS.md`、`CLAUDE.md` など)、プロジェクトの設定などにリポジトリが書かれていれば、それを使う。
- 書かれていなければ、ユーザーに1回だけ聞く。ブランチもまとめて聞き、分からない場合の扱いも伝える。例: 「テスト環境には、どのリポジトリのどのブランチがデプロイされていますか? ブランチが不明な場合は、デフォルトブランチを確認します。」
- ユーザーがリポジトリ名をすぐに答えられない場合は、補助としてコード検索を使ってよい。失敗した要素のIDや文言で、ユーザーが読めるリポジトリを検索し、候補を示して選んでもらう。ありふれたIDは多くのリポジトリに当たるので、検索結果だけで決めない。
- 聞く相手がいない場合(定期実行など)は、コード検索で候補が1つに絞れたときだけ使い、「推定したリポジトリ」として報告に書く。絞れなければ、コード変更の調査を省く。
- ブランチが分からなければ、デフォルトブランチを見て、そのことを報告の「補足」に書く。
- テスト環境のデプロイ元がデフォルトブランチと違う場合(例: `develop` や `staging`)は、そのブランチに入ったコミットを調べる。PRもマージ先がそのブランチのものに絞る。

#### 期間内の変更を探す

「最後に成功した実行の開始時刻」から「最初に失敗した実行の開始時刻」までの間に、上で決めたブランチへマージされたPR・コミットを探す。デプロイには時間差があるので、少し前まで幅を持たせる。

見つかったPR・コミットの差分を読み、失敗した要素のID・文言・関連する処理(計算、表示条件など)に触れているものを探す。コミットメッセージは曖昧なことが多い(「デザイン調整」「改善」など)ので、メッセージではなく差分で判断する。

差分から、変更が意図的かどうかを考える。

- 文言・ID・レイアウトを意図して変えている → 仕様変更。テストを新しい仕様に合わせる必要がある。
- 計算や条件の変更で、テストの期待値の方が妥当(例: 合計金額が明らかにおかしい) → アプリの不具合(デグレ)の疑い。
- どちらとも言えない → その旨を書き、開発者への確認を推奨する。

関係しそうな変更が見つからない場合は、それ自体が「コード変更以外(Flaky・環境・データ)」の根拠になる。

### 6. 分類して報告する

分類は次のいずれか。

| 分類 | 意味 | 推奨する対応の例 |
|---|---|---|
| アプリの不具合 | アプリが期待どおりに動いていない | 開発者に不具合として報告する |
| 仕様変更(テストの更新が必要) | アプリは意図どおりで、テストが古い | テストケース・UIを新しい仕様に合わせる |
| Flaky(タイミング) | 待ち時間・表示タイミングで結果が揺れる | 待機の追加、確認方法の見直し |
| Flaky(テストデータ) | 日付・データの状態で結果が変わる | テストデータや日付の扱いを見直す |
| 環境 | 画面サイズ・ブラウザ・端末など実行環境の違い | テスト設定ごとの手順分け、設定の見直し |
| MagicPod・インフラ側 | 実行基盤やMagicPodの問題が疑われる | 再実行で再現するか確認、サポートへ問い合わせ |
| 判断できない | 根拠が足りない | 何を確認すれば判断できるかを書く |

1つのバッチ実行に、性質の違う原因が混ざっていることはよくある(コード変更による失敗と、たまたま起きたFlakyなど)。全部を1つの原因で説明しようとしないこと。

## 報告の形式

報告を読む人は、まず「結局、何が原因で、自分は何をすればいいのか」を知りたい。調査の過程や細かいログは、知りたくなった人だけが読めばよい。だから、**結論とやることを先頭に置き、根拠は短く後ろに回す**。調べたことを全部書くと、肝心の結論が埋もれて読まれなくなる。

書き方の決まり:

- ユーザーの言語で書く。全体で**2,000字前後(長くても3,000字)**に収める。
- 1文は短く。1つの箇条書きには1つのことだけを書く。
- 「結論」は、ログや専門用語を知らない人が読んでも分かる言葉で、3文以内にする。
- 「やること」は、誰が・何を・どのテストケース(またはPR)に対して行うかを、優先順に最大4つ書く。「検討する」で終わらせず、具体的な操作を書く。
- 根拠は、原因ごとに重要なものを3〜5個だけ選ぶ。ログの時刻の羅列、長い差分、調査の前提の説明は書かない。差分は関係する1〜2行だけ引用する。
- 今回の失敗と直接関係しない気づき(潜在的なFlaky要因など)は、「補足」に1〜2行で書く。

次の形を使う。

```markdown
# バッチ実行 #<番号> の失敗調査

## 結論
<何が原因で、テストとアプリのどちらに問題があり、何をすればよいかを3文以内で>

## やること
1. **<誰が>**: <何を、どの対象に>
2. ...

## 失敗したテストケース
| テストケース | 分類 | 原因(ひとこと) |
|---|---|---|
| <TC名(実行へのリンク)> | <分類> | <20字程度で> |

<対象: テスト設定、実行日時。失敗 X件 / 全 Y件>

## 根拠
### 原因1: <ひとことで>(信頼度: 高/中/低)
- <最も強い根拠。エラー・画面・ログの所見>
- <関連するPR・コミット(リンクつき)と、差分のどこが関係するか>
- <実行履歴やほかのテスト設定との比較>

### 原因2: ...

## 未確認事項
- <確かめていないことと、確かめる方法。最大3つ。無ければ省略>

## 補足
<直接の原因ではない気づき、調査できなかったこと(GitHubが読めなかったなど)。無ければ省略>
```

信頼度の目安: 複数の独立した根拠(エラー+差分+履歴など)がそろえば「高」、1つだけなら「中」、推測が多ければ「低」。
