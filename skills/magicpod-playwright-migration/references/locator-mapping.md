# ロケーターの対応

MagicPodのステップは、ロケーター文字列を直接持たず、`capture_ui` で取り込んだ「UI」の中の要素（`uiId` + `uiElementId`）を参照する。そのため、**実際に画面を取り込み、Playwrightが指していた要素をその中から特定する**。使えるロケーターの形式は `xpath=` / `css=` / `id=` / `ai`。

## ルール

- 取り込んだUIの中で候補が**1つに決まらない**ときは推測しない。候補を示してユーザーに確認する
- 作ったロケーター・付け替えたロケーターは、`inspect_locators` の verify モードで、**1つの要素だけに当たる**ことを確かめる
- ロケーターには、Playwrightのコードにある指定（`#email` → `id=email` など）か、要素の属性から作った CSS / XPath を使う
- 要素の名前は、ステップを作る**前に**わかりやすい名前に変える（例：「ログインボタン」）。名前変更とロケーターの追加でUIのIDが変わることは ui-handling.md
- ロケーター `ai` は、ユーザーが望んだ場合を除いて使わない

## Playwrightのロケーター別の対応

| Playwright | 特定のしかた |
|---|---|
| `page.locator('#id')` / `locator('css')` / `locator('xpath=…')` | そのまま使える。取り込んだUIの要素と一致するかを `inspect_ui`（mode=`search`）で確かめる |
| `getByTestId(id)` | `css=[data-testid="…"]`。`playwright.config.ts` の `testIdAttribute` を変えていれば、その属性名にする（例：`data-test` なら `css=[data-test="…"]`） |
| `getByRole(role, { name })` | 対応する形式がない。役割とアクセシブルネームが一致する要素を探す。タグと役割がずれる要素に注意（下の「`getByRole` の注意」） |
| `getByLabel(text)` | ラベルから入力欄を特定する。**既定で部分一致**（大文字・小文字も区別しない。`exact: true` のときだけ完全一致）なので、ラベルに「必須」などが付いていても当たる。完全一致の XPath にすると余分な文字で見つからず、部分一致にすると名前の一部が重なる別の入力欄（「メールアドレス」と「メールアドレス（確認）」など）を指すおそれがある。形は下の「役割やラベルで探すときのXPath」 |
| `getByText(text)` / `getByPlaceholder()` | UIの中でテキストや属性が一致する要素を探す |
| `.first()` / `.nth(i)` / `.last()` | 位置で選ぶ指定なので、XPath の位置指定にする（`.first()` → `(…)[1]`、`.nth(i)` → `[i+1]`、`.last()` → `[last()]`）。`capture_ui` が作るロケーターは中身で探すので、`edit_ui_elements` で位置指定の XPath に置き換える |
| `.filter({ hasText })` / `locator.locator()` の連鎖 | 同じ条件を XPath で表す |
| `a.or(b)` | 実機で実際に当たる要素を調べ、その要素だけを指すロケーターにする。どちらに当たったかは説明欄に書く |
| `page.locator('main')` のような広い範囲 | 確認したいテキストを含む、もっと小さい要素にしてよいかユーザーに確認する |

## `getByRole` の注意

`getByRole` は、タグではなく**役割（role）**で探す。役割はふつうタグから決まる（`<a href>` はリンク、`<button>` はボタン）が、`role` 属性で上書きできる。MagicPodのロケーター（XPath・CSS）はタグや属性で探すので、タグと役割がずれている要素では結果が分かれる（例：`<a href="#" role="button">ログイン</a>` は `getByRole('link', { name: 'ログイン' })` では見つからないが、`//a[text()='ログイン']` では見つかる）。

- ページのHTMLを取得して（SKILL.md の手順3）、対象の要素に `role` 属性が付いていないか、`href` のない `<a>` や `role` 付きの `<div>` ではないかを確かめる。HTMLを取得できないときは、`store_attribute_to_variable`（attribute: `role`）を一時的に置いて実行し、実行ログで値を見る（確かめたら消す。要素のHTML全体 `outerHTML` は読めない）
- ずれていそうで確かめられないときは、推測せずユーザーに確認する
- 条件分岐や表示の確認に使う要素は、実行して元のコードと同じ結果になるかを確かめる（command-mapping.md の「条件分岐」）

### 役割やラベルで探すときのXPath

`capture_ui` が作ったロケーターが元のコードの探し方と合わない場合は、次の形を使う。Playwright の `name` は既定で部分一致なので `contains` にそろえる（大文字・小文字を区別しない点は再現しない）。`exact: true` なら `normalize-space()='名前'` にする。

| Playwright | XPath |
|---|---|
| `getByRole('button', { name })` | `//*[(self::button or @role='button') and contains(normalize-space(),'名前')]` |
| `getByRole('link', { name })` | `//a[@href and not(@role) and contains(normalize-space(),'名前')]` |
| `getByLabel(text)` | `//*[@id=//label[contains(normalize-space(.),'ラベル')]/@for]` |

## もっと安定したロケーターに置き換える

元のコードより安定したロケーター（`id`、`data-testid` など）があれば、置き換えを提案してよい（候補は `inspect_locators` の suggest モード）。ただし、**元のテストが確かめていることを変えない場合に限る。**

- 位置で選んでいる（`.nth(0)` で1件目が「いちご」）：表示順も確かめているので、「いちごを含む行」にすると順番の確認がなくなる
- ラベルで選んでいる（`getByLabel('商品名')`）：ラベルと入力欄の結び付きも確かめているので、`id=productName` にするとそれを確かめなくなる

置き換えは、計画で「確かめられなくなること」とあわせて示し、承認を得る。置き換えたら、説明欄に元のロケーターを残す。

## 複数の要素に当たるロケーター（strict mode）

Playwrightは、1つの要素を対象にする操作や確認（`click()`・`fill()`・`toHaveText('x')`・`toBeVisible()` など）で、要素が2つ以上見つかるとエラーにする（strict mode）。`toHaveCount()`、配列の `toHaveText([…])`、`allTextContents()`、`first()` / `nth()` / `last()` で絞ったものは対象外。MagicPodは、複数の要素に当たっても失敗せず、**一番上の要素**に対して実行するので、「1つだけであること」の確認が抜ける。

1. **ふだんは、1つの要素だけに当たるロケーターを作れば足りる。** 元のコードの「1つだけ」は、多くの場合ロケーターをそう書いた結果で、確かめたいことそのものではない
2. **元のロケーターが一覧の項目など、複数の要素に当たりうる場合**（例：一覧の各行に付いた `.item-name` に、1つの値の `toHaveText('x')`）は、「1件だけ」も確かめたいことに含まれる。1件目（`(…)[1]`）で元のコードと同じ確認をし、2件目（`(…)[2]`）がないことを `assert_invisible`（表示で数える）か `assert_not_exists`（DOMで数える）で確かめる。要素は「I件目」（`(…)[${I}]`）を1つ用意して `I` を変えてよい（command-mapping.md の `toHaveCount(n)` と同じ組み立て）
3. 配列の `toHaveText([…])` / `toContainText([…])` は件数も確かめているので、1件ずつの確認に加え、n+1件目がないことを確かめる
4. 2に当たるか判断がつかないときは、計画の「確認したいこと」に挙げる

## 取り込まれない要素の扱い

`capture_ui` は画面に見えている要素をもとにUIを作るので、次のような要素はUIに入らないことがある：表示範囲の外にある要素、操作の後で現れる要素、`<head>` 内の要素（`<meta>`、`<link>`）、一瞬で消える要素（トーストなど）。

**基本は、要素が出ている状態の画面を取り込む**（UIの画像の上で位置が分かり、人が見て分かりやすい）。

- 画面の下のほうの要素：`capture_ui` を `take_whole_page_capture=True` で実行する
- 操作の後で現れる要素：その操作までを `execute_partial_steps` で実行してから取り込む

**付け替えは、次の2つの場合に限る。**

- 取り込めない要素：`<head>` 内の要素や一瞬で消える要素など
- 同じ要素を別のロケーターでも探す必要があるとき（あるテストでは `id` で、別のテストではラベルで探している、など）。共有UIでは1つの要素にロケーターを1つしか持てないため。付け替えた要素は、名前の末尾に探し方を付ける（例：「数量（ラベル）」）

付け替えの手順：

1. 同じページのUIの中から、自動で名前が付いていて（`area(7)` など）ステップで使っていない要素を1つ選ぶ。**対象と同じフレームの要素を選ぶ**（要素はフレームの情報を持ったままなので、iframe の中の要素に付け替えると、メインのフレームの対象は見つからない。フレームは `inspect_ui` の結果や実行ログの `frame:` で確かめる）
2. `edit_ui_elements` で、その要素に `add_locator`（例：`css=meta[name="robots"]`）と `rename`（例：「robotsメタタグ」）を行う。元のロケーターは置き換わる
3. その画面のステップを作る前に済ませる（UIのIDが変わるため）

- 付け替えた要素は、`inspect_ui` の mode=`get` では出ないことがある。探すときは mode=`search`（または `full_regions=True`）を使う
- 付け替えた要素は、UIの画像の上では元の要素の位置のまま表示される。どの要素を付け替えたかを説明欄に書く
