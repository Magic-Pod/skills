# 変換計画のテンプレート

手順4でユーザーに示す変換計画は、次の形式で書く。件数の内訳は必ず表で示し、「後述」「ほか」のような、数え方があいまいな書き方はしない。

````markdown
## 変換計画

### 前提

| 項目 | 内容 |
|---|---|
| 変換元 | `tests/…`（ファイル数・テスト数） |
| 変換先 | 組織 / プロジェクト / フォルダ |
| テスト設定 | 名前（番号）。ベースURL・言語 |
| 開始方法 | プロセス再起動（`app_reinstall`） |

### 件数の内訳

| 区分 | 元のテスト数 | 作るテストケース数 |
|---|---|---|
| そのまま変換 | 0 | 0 |
| まとめて1件にする（データパターン・統合） | 0 | 0 |
| 確認したうえで変換（「確認したいこと」で承認を得たもの） | 0 | 0 |
| 一部だけ変換（一部の行を変換しない） | 0 | 0 |
| 変換しない | 0 | — |
| ユーザーの選択で決まる（例：代わりの案で変換するか、変換しないか。確認1で選んでもらう） | 0 | 0〜0 |
| **合計** | **0** | **0〜0** |

※ ユーザーの選択で作るテストケース数が変わる場合は、その行と合計を範囲（例：10〜14）で書いてよい。選択がなければ、この行は消す。
※ 「元のテスト数」の合計は、変換元の `test()` の数（ループで作られるものは展開後の数）と一致させる。1回の依頼で変換するのは20テストまで。超える場合は、今回変換する範囲と、残り（次回以降）を分けて書く。

### 作るテストケース（作成順）

| 順 | テストケース名 | 変換元 | 概要 | 備考 |
|---|---|---|---|---|
| 1 | | `file.spec.ts:行` › テスト名 | | |

### 共有ステップ・共有UI

| 名前 | 新規／既存 | 使うテストケース | 取り込む状態（共有UI） | 既存との違い・備考 |
|---|---|---|---|---|

### 共有変数・テスト設定の値

| 変数 | 状態（一致／表記揺れの疑い／未登録／テスト設定の値） | 備考 |
|---|---|---|

### こう進めるもの（異論がなければこのまま進める）

- 決まった進め方があるものを箇条書きで書く（例：`getByText(x).toBeVisible()` は値の確認にする）

### 変換しないもの

テスト全体を変換しないものに加え、「一部だけ変換」したテストの変換しない行も、ここに1行ずつ書く。

| 変換元 | 理由 |
|---|---|

### 確認したいこと

本当に決まっていない点だけを書く。各項目に、推奨案、その理由、その案で確かめられなくなることを添える。

| # | 項目 | 推奨案 | 理由 | 確かめられなくなること |
|---|---|---|---|---|
````

「理由」の書き方：

- 1〜2文にする
- 「Playwrightではこう動くが、MagicPodではこうなる」という違いを書く。「推奨します」「安定するため」のような、理由になっていない言い換えにしない
- 選ばなかった案があれば、その案と選ばなかった理由も短く書く（例：既存の共有ステップを使わない理由）

例：

| # | 項目 | 推奨案 | 理由 | 確かめられなくなること |
|---|---|---|---|---|
| 1 | ログイン状態の保存と再利用（`storageState`、`describe.serial`） | 2件を1つのテストケースにまとめる。ログインは元のコードどおりラベルで探すロケーターで、テストケースに直接作る（既存の共有ステップ「ログインする」は使わない） | `storageState` はログイン状態を別のブラウザ状態に移す仕組みで、MagicPodにはない。2件に分けると、2件目はログインしていない状態で始まる。既存の共有ステップは入力欄を id で探すので、元のコードが確かめている「ラベルで入力欄が見つかること」を確かめなくなる | 別のブラウザ状態に、保存したログイン状態を復元できるか |
