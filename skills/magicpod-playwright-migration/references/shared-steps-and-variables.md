# 共有ステップ・変数・投入順序

## 共有ステップにする基準

次のどちらかに当てはまる操作だけを、共有ステップの候補としてユーザーに提案する。それ以外は共有ステップにしない。

| 基準 | 条件 | Playwrightでよくある形 |
|---|---|---|
| くり返し出てくる操作 | **2つ以上のテストケース**に、**2ステップ以上**の同じ操作の並びが出てくる。ある画面までたどり着く手順も含む | fixture（例：ログイン済みの状態を作る）、`beforeEach`、Page Object のメソッド |
| 値だけを変えてくり返す操作 | **同じテストケースの中で3回以上**、値だけを変えて同じ操作をくり返す | 1つの `test()` の中で、同じメソッドを引数を変えて何度も呼ぶ |

共有ステップにしないもの：1つのテストケースでしか使わない操作、1ステップだけの操作（`page.goto` だけの `beforeEach` など）、そのテストケース固有の状態に強く依存する操作。

提案する前に `search_shared_steps` で、同じ働きの共有ステップがすでにないかを確かめる。あれば、新しく作らずに使うことを提案する（下の「既存の共有ステップを使うとき」）。

### データパターンとの使い分け

| 状況 | 提案するもの |
|---|---|
| **別々のテスト**が、同じ手順をデータだけ変えて実行している（配列の `for` で `test()` を作る、など） | データパターン（`edit_data_pattern`）。1つのテストケースにまとめる |
| **1つのテスト**の中で、同じ操作を値だけ変えて3回以上くり返している | 共有ステップ＋パラメーター。値ごとに共有ステップを呼ぶ |

### 粒度と階層

- 粒度はユースケース単位にする。「メールアドレスを入力する」ではなく「資格情報でログインする」のようにまとめる
- 階層は2段までにする
  - 画面内の操作：1つの画面の中で、画面が切り替わるまでの一連の操作
  - 画面をまたぐ操作：画面内の操作を順に呼ぶ、複数の画面にまたがる操作
  - 迷ったときの基準：最後に**別の画面**の確認（URL・見出し・タイトルなど）があれば、画面をまたぐ操作にする
- 同じ操作でも遷移先が違う場合は、別の共有ステップにする

### 命名

日本語で、「〜する」の形にそろえる。

| 種類 | 形 | 例 |
|---|---|---|
| 画面内の操作 | `［画面名］ 〜する` | `［ログイン画面］ 資格情報でログインする` |
| ダイアログの操作 | `［ダイアログ］ 〜する` | `［ダイアログ］ 退会確認ダイアログを承認する` |
| 画面をまたぐ操作 | `〜する`（接頭辞なし） | `管理者ユーザーでログインする`、`マイページからログアウトする`（トップページの確認で終わるので `［マイページ］` を付けない） |
| URLを直接開いてから操作する（画面をまたぐ操作） | `〜を直接開いて〜する` | `ログイン画面を直接開いてログインする` |

- 画面名は、テスト対象の画面に表示されている名前（見出しやタイトル）を使う。Playwrightのクラス名（`LoginPage` など）や、このSkillの中でしか使わない呼び名は使わない
- 同じ遷移先でも、ヘッダーなどから開くのか、URLを直接開くのかで手順が違う。URLを直接開く場合は、名前に「直接開いて」を入れて、既存の共有ステップとまぎらわしくならないようにする

### 作り方

1. まず、共有ステップにしたい手順をテストケースの中に直接作る
2. `execute_partial_steps` で、実機で通ることを確認する
3. `create_shared_step` で、その範囲を共有ステップとして切り出す。切り出すと、そのテストケースのステップの `ref` がすべて変わるので、続けて切り出すときは、そのたびに `read_test_case` で取り直す
4. 同じ手順が他の場所にもあれば、**次の切り出しに進む前に**、それらを共有ステップの呼び出し（`shared_step` コマンド）に置き換える。こうしないと、同じ内容の共有ステップが重複してできる
5. 値を変えたい箇所はパラメーターにする。切り出すときに `create_shared_step` の `params` で指定するか、切り出した後に `edit_shared_step` の `add_parameter` で追加する
   - 入れ子の共有ステップに渡している引数をそのままパラメーターにするときは、`params` の項目で `step_ref` に呼び出しステップの ref、`source_param` に引数のキー名を指定する。例：`{"name": "LOGIN_EMAIL", "type": "string", "step_ref": "<共有ステップを呼んでいるステップのref>", "source_param": "LOGIN_EMAIL"}`

- 共有ステップの中で使うUIは、共有UI（`capture_ui` の `save_as_shared=True`）でなければならない（ui-handling.md）
- 共有ステップを呼ぶ前には、`start_session` のたびに `search_shared_steps` で検索しておく。しないと「このプロジェクトに登録されていない」で呼べないことがある（検索のしかたは mcp-notes.md）

### 確認ステップの並べ替え

共有ステップにするために、元のコードと手順の順番を変えたくなることがある（例：クリックの後の「URLの確認」と「見出しの確認」を入れ替えて、クリックと見出しの確認を続けて1つの共有ステップにする）。

- **画面の状態を変えない確認ステップどうし**（`assert_*` など）は、並べ替えてよい
- 操作（クリック・入力など）や、変数に値を入れるステップをまたいで動かしてはいけない
- 並べ替えた場合は、どのテストケースのどの確認を入れ替えたかを結果の報告に書く

### 既存の共有ステップを使うとき

名前や説明が合っていても、中身が元のコードと同じとは限らない。使う前に次のことを行う。

1. `read_shared_step` で中身（ステップとパラメーター）を読む。別の共有ステップを呼んでいれば、**入れ子の共有ステップも**読む（中身の大半が入れ子の側にあることがある）
2. 元のコードの該当部分（手順2で展開したもの）と1ステップずつ比べる。比べる観点：
   - 元のコードにない操作や確認が入っていないか（例：最後にページタイトルの確認がある）
   - 元のコードにある操作や確認が抜けていないか
   - 操作する要素や操作のしかたが違わないか（例：`check()` に対してクリック）
   - 要素の探し方が違わないか。`read_shared_step` には要素名しか出ないので、`inspect_ui` で要素のロケーターを見る（例：元のコードはラベルで探しているが、共有ステップの要素は `id` で探している）
   - パラメーターにしていない固定値が、元のコードの値と違わないか
3. 違いが1つでもあれば、実害がなさそうでも `確認する` の項目として計画に挙げる。違いの内容と、次の選択肢を示す：そのまま使う（違いを説明欄に書く）／新しい共有ステップを作る／共有ステップを使わずテストケースに直接書く
4. その共有ステップを使っている既存のテストケースの数（`list_shared_steps` の `test_case_count`）も示す。後で直すと、それらにも影響するため

既存の共有ステップの中身は、ユーザーの承認なしに変更しない。

## 共有変数

ログイン用のメールアドレス・パスワードなど、多くのテストケースで使う値は共有変数の候補になる。ただし共有変数はユーザーがMagicPodの画面で登録・編集する必要があるので、むやみに増やさない。`baseURL` は共有変数にせず、テスト設定の組み込み変数 `${BASE_URL}` を使う。

ステップを作る前に、次の手順で突き合わせる。

1. 変換後のステップで使う予定の `${変数名}` をすべて洗い出す
2. `read_test_case` の応答にある登録済みの共有変数（`shared_variables`）と突き合わせる。テスト設定に定義された値（`${BASE_URL}` など）はここには出ないので、手順1で選んだテスト設定の値として別に確かめる
3. 結果を次の3つに分けてユーザーに示す
   - 一致：そのまま使う
   - 表記揺れの疑い：名前が似ている変数がある（例：`BASE_URL` と `baseUrl`）。どちらを使うか確認する
   - 未登録：MagicPodの画面で登録してもらってから進む

`shared_variables` と、プロジェクトの実際の使われ方が食い違うことがある（例：`shared_variables` は空なのに、既存のテストケースは `${BASE_URL}` を使っている）。気づいたら推測で判断せず、事実をユーザーに伝えて、どの変数を使うか確認する。

### 秘密情報

- パスワードなどの秘密情報は、ステップに直接書かず、共有変数（シークレット）にしてもらうよう提案する
- データパターンに入れる場合も同じ。データパターンの値は、テストケースを見られる人なら誰でも読める
  - テスト用の公開された値（練習サイトの固定アカウントなど）なら、そのことを伝えたうえで、そのまま入れてよいか確認する
  - 本物のアカウントの値なら、データパターンには入れず、共有変数（シークレット）にしてもらう案を示す

## 投入の順序

複数のテストケースを変換するときは、次の順に作る。

| 順番 | 対象 | 例 |
|---|---|---|
| 1 | 認証まわりの共有ステップ | 会員登録、ログイン |
| 2 | データを作るテスト、参照するだけのテスト | 予約内容の確認 |
| 3 | データを変えるテスト | 会員情報の変更 |
| 4 | データを消すテスト | 退会 |

- 1で作った共有ステップを、2以降のテストケースで呼ぶ
- 消す対象のデータをテストの中で用意できないものは、最後に回す
- それ以外に制約がなければ、元のコードに書かれている順に作る

MCPの動き（`ref` が変わる、端末が終了する、共有ステップの保存が失敗する、など）への対処は mcp-notes.md にまとめてある。
