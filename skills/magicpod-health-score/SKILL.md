# MagicPod ヘルススコア改善

プロジェクトのヘルススコアを読み、**どうすればグリーンに届くか／グリーンを保てるか** を提案するスキル。
スコアは「テストから信頼性のあるフィードバックを毎日得られているか」を測る指標で、テスト数やバグの検出数を競うものではない。提案もこの考え方に沿って行う。

## このスキルがやること・やらないこと

- **やる**：スコアと内訳の読み取り、点が伸びる順の改善策の提案、導入時の目標と3か月の道筋の設計、グリーンを維持するための習慣の提案。
- **やらない**：テストの失敗原因の調査、テストケース・共有ステップ・ロケータの編集や削除、一括実行の設定の変更。
  - 提案を実行したいと言われたら、手順 6 のとおり、ほかのスキルや MagicPod の画面での操作につなぐ。
- このスキルの中では、MagicPod のデータを **読み取るだけ** にする。

## 前提

- MagicPod MCP サーバーに接続していること。
- 接続していない場合は、目標設計（モード A）だけを、ユーザーへの質問をもとに進められる。スコアを使う提案には MCP が必要だと伝える。

## 手順

### 1. 対象のプロジェクトを決める

- ユーザーが組織名・プロジェクト名、または MagicPod の URL（`https://app.magicpod.com/{組織名}/{プロジェクト名}/...`）を示していれば、それを使う。組織名が分かっていれば `list_organizations` は呼ばない。
- 示していなければ `list_organizations` → `list_projects` で候補を出し、どれを見るか聞く。候補は `表示名（名前）` とプラットフォーム（ブラウザ／モバイル）を並べ、「複数」「全部」でもよいと添える。候補が1つならそれを使ってよい。
- プロジェクトには、画面に出る **表示名** と、URL やツールの呼び出しに使う **名前**（内部名）の2つがあり、違うことがある。候補やまとめでは両方を `表示名（名前）` の形で出す（同じなら1つでよい）。ツールの呼び出しとリンクには名前を使う。
- **複数のプロジェクトを見るとき** は、重くならないよう次の順にする。
  1. **プロジェクトが 5 個を超えるときは、スコアを取る前に、運用しているプロジェクトを聞く**。名前に Demo・Sandbox・Copy・Test などが付くものは、デモ・検証用の候補として示してよい。
  2. 対象のプロジェクトの最新の週のスコアだけを取り、比較表にする（`references/report-template.md` の「複数のプロジェクト」）。一括実行が週0回のものがあれば、表を出したところでいったん止め、運用しているかを確認する。
  3. 深く見る（手順 2 の推移・追加の取得と、手順 3〜5）のは、運用しているプロジェクトのうち、ユーザーが選んだものだけにする。指定がなければ、80 点以上のもの（モード C）と、いちばん点が高い 80 点未満のもの（モード B）に絞る。
  - 運用していないプロジェクトには、改善の提案をしない。
- **1つだけ見るときも**、一括実行が何週も0回で、名前からデモ・検証用に見える場合は、運用しているかを確認する（改善したいと言われていれば、運用しているものとして進めてよい）。

### 2. スコアを集める（読み取りのみ）

次の順で取得する。詳しい読み方は `references/scoring-logic.md`。

1. `get_health_score`（`period: "week"`、日付の指定なし）：最新の週のスコアと内訳。
2. 推移を見るため、最新の週の返り値の `period.end_date` から7日ずつさかのぼった日を `last_date_of_period` にして、過去3週分を取る（合計4週分）。過去の週は `score` と各項目の `value` だけ読めばよい（一覧などは最新の週のものを使う）。
3. 必要に応じて追加で取る：
   - **実行頻度か失敗率が満点でないとき**（モードに関係なく）：
     - `list_batch_runs`（直近50件）で、一括実行がどの曜日に、どの方法で走っているかを確認する。失敗がいつから続いているかを知りたいときだけ、`cursor` で前の1ページを見る。`execution_method` の値は `scheduled_run`（スケジュール実行）、`command_line`（CI など）、`gui`（画面から手動）、`mcp`（AI から）などがある。
     - 以前はスケジュール実行があったのに途中で止まっている場合は、そのことと最後に実行された日を伝える。止めたのが意図的かどうかは分からないので、ユーザーに確認する形で書く。
     - テスト設定（`test_setting_name`）ごとに、成功・失敗が分かれていないかを見る（例：ある設定は毎日成功し、別の設定は毎日失敗している）。
     - 環境のラベル（`test_condition_labels`）から、クラウド端末かローカル実機か、どの端末・ブラウザかを見る。自動化したい対象（OS・端末）と合っていなければ、新しい一括実行の設定を作るよう提案する。
     - 一括実行にどのテストが入っているかは、`list_test_settings` では分からない（返るのは実行環境のパターンだけ）。設定ごとに最新の一括実行を `list_batch_run_test_runs` で見て、実際に動いたテストを確かめる。作ったテストの多くが入っていないときは、実行頻度が低い理由として伝える。
     - 失敗しているテストは、`get_health_score` の失敗率の項目に付く一覧（`failed_or_incomplete_test_cases`）で分かる。失敗回数の多い上位5件ほどを示す。原因の調査はしない。
       - この一覧にはテスト設定の情報がない。どのテスト設定で失敗したかは、上の `list_batch_run_test_runs` の結果で確かめる。
       - その週に一括実行が1回もないと、一覧は返らない。最後に一括実行があった日（`list_batch_runs` で分かる）を `last_date_of_period` にして取り直すと、止まる前に失敗していたテストが分かる。
   - **`list_test_cases`（`depth: null`）を呼ぶとき**：モード A のとき、実行頻度か失敗率が満点でないとき、テストケースが 20 件未満と思われるとき。
     - 返り値は1件ごとの要約を含んで大きい。使うのは件数、`step_count`、`labels`、`created_at`、`updated_at` と、必要なら `ai_generated_summary`（テストの中身が自動化したい対象と関係あるかを見分けるため）。
     - 次のテストは、棚卸しの候補として挙げる：ステップが 0 件、「作成中」「WIP」のラベル、「Flaky」のラベル、説明欄にローカル実行が前提と書かれたもの、長く更新されていない試しに作ったようなもの。スコアへの効き方はテストによって違う（ステップ 0 件のテストがあっても実行頻度が満点のこともある）ので、「スコアのため」と断定せず、保守の面も合わせて挙げる。

注意（集計のタイミング）：

- 集計された最新の週より後に一括実行があれば、「明日以降のスコアに反映される」と一言添える。

注意：

- スコアは1日1回集計される。今日の変更は、翌日以降のスコアに反映される。
- 返り値に含まれるテストケースの URL は、そのままでは開けないことがある。リンクを出すときは `https://app.magicpod.com/{組織名}/{プロジェクト名}/{テストケース番号}/` の形で組み立てる。
- 内訳の `improvements` にある `current` と `required` は、MagicPod が示す「あとどれだけ必要か」の値。提案の数字はこれを優先して使う。

### 3. モードを決める

| モード | 当てはまるとき | 参照 |
|---|---|---|
| **A. 目標設計（導入時）** | ユーザーが計画・目標づくりを求めている、または導入したばかりと言っている。テストケースが 8 件未満で一括実行もほとんどないときも | `references/onboarding-roadmap.md` |
| **B. 改善提案** | スコアが 80 点未満 | `references/improvement-actions.md` |
| **C. 維持** | スコアが 80 点以上 | `references/improvement-actions.md` の「グリーンを維持する」 |

- 判断がつかないときは、どちらで進めるか1問だけ聞く。
- A と B は組み合わせてよい。
  - 導入したばかり（道筋の1か月目）なら、スコアは低くて当然なので、内訳は主なものを1行にまとめ、提案は「今週やること」に入れる。
  - 2か月目以降でスコアが低いなら、B の内訳と提案（優先順）をそのまま入れる。
- C でも、満点まで大きく足りない項目があれば、B の並べ方で 1〜2 件提案してよい。
- 「導入したばかり」でも、試しに作ったテストが残っていることがある。テストの件数だけで道筋のどこにいるかを判断せず、手順 2 で見たテストの中身と一括実行の状況で判断する。

### 4. 提案をつくる

#### A. 目標設計

- 目標は **「3か月で、毎日安定して成功するテスト 8 件を持ち、ヘルススコアのグリーンを保てる体制」**。数を増やすことより、毎日成功することを優先する。
- 質問の前に、手順 2 で分かったこと（今のスコア、既存のテストと一括実行の状況）を2〜3行で伝える。既存のテストの扱いを聞く前提になるため。
- 次のことを、**一度に聞くのは3問まで** にして確認する。分からなければ、一般的な前提で進めて「仮置き」と明記する。
  1. 自動化したいアプリと機能、対象の OS（iOS と Android の両方か）、最初の 3 件の候補。既存のテストがあれば、その扱い（使い続けるか、整理するか）もここで聞く
  2. プロジェクトに参加できる人数と、メンテナンス担当を決められるか
  3. 毎日実行する仕組み（MagicPod のスケジュール実行、または CI）と、クラウド端末かローカル実機か
- `references/onboarding-roadmap.md` に沿って、月ごとの到達目標・やること・見込みのスコアを出す。
- 「今は自動化しないもの」も一緒に挙げ、後回しにしてよいと伝える。

#### B. 改善提案

`references/improvement-actions.md` のルールで並べる。要点：

1. **テストケースが 8 件未満なら、8 件にすることを最優先** にする（8 件未満だと、ほかの項目が満点でも減点されるため）。
2. 次に、**実行頻度と失敗率（合わせて 70 点）**。毎日の一括実行を設定し、失敗を翌日に持ち越さない。
3. そのあと、**共有ステップと安定ロケータ（合わせて 16 点）**、最後に **テスト数・メンバー数・テストの長さ（合わせて 14 点）**。
4. リリース頻度が低い、ローカル実機が中心、実行していない古いテストが多い、のどれかに当てはまりそうなら、`references/improvement-actions.md` の「スコアが上がりにくい、よくある状況」の考え方で提案する。当てはまる状況への提案は、関係する項目（実行頻度など）の提案の中に組み込み、その項目の順位に置く。
   - ユーザーが自分の状況（一人 QA など）を話しているときは、それに答える提案を、順位に関係なく必ず入れる。
5. 各項目で「満点 − 現在の点数」が伸びしろ。伸びしろが大きく、すぐできるものから並べる。伸びしろが 0.5 点未満の項目は提案に入れない。
6. 提案は多くても 3〜5 件にする。各提案に「なぜ減点されているか」「何をするか」「見込みで何点くらい上がるか（目安）」をつける。
7. スコアが前の週より下がっていれば、新しいテストの作成をいったん止めて、既存のテストを直すことを先に勧める。

#### C. 維持

- **グリーンまでの余裕** を示す：今のスコア − 80 点が何点か、どの項目がどれだけ下がると 80 点を割るか。
- 4週分の推移を見て、下がり始めている項目を挙げる。
- 維持の習慣（週1回のスコア確認、失敗を翌日に持ち越さない、メンテナンスの時間の確保）ができているかを、データから判断する（判断のしかたは `references/improvement-actions.md` の「グリーンを維持する」）。足りないものを提案する。
- テストを増やすときは、スコアを保ったまま少しずつ増やすよう勧める（増やした直後に実行頻度・失敗率・共有ステップの割合が下がりやすい）。

### 5. 結果を伝える

- `references/report-template.md` の形でまとめる。最初に結論（今のスコアと色、いちばん効く一手、モード C ではグリーンまでの余裕）を書く。
- 点数の見込みは、計算の仕組みからの **目安** であり、保証ではないと分かる書き方にする。失敗率のように今の成功率が分からない項目は、幅で示す。
- 専門用語は MagicPod の画面の言葉にそろえる（一括実行、共有ステップ、ロケータ、アナリティクスタブなど）。

### 6. 「提案内容を実行しますか？」のあと

最後に、どの提案から進めるかを聞く。進めると言われたら、**このスキルでは変更せず**、次のようにつなぐ。ヘルプ記事の URL は `references/help-articles.md` にある。

| 提案 | つなぎ先 |
|---|---|
| 失敗しているテストを直す・不安定なテストを直す | 失敗の調査・Flaky テスト対策のスキル |
| 不安定なロケータを直す、長いテストを分ける | テストのレビュー・メンテナンスのスキル |
| 重複したステップを共有ステップにまとめる | テストスイート整理のスキル（`magicpod-test-organization`） |
| ラベルでメイン機能のテストを選び、それだけを毎日実行する | テストスイート整理のスキル（ラベルを付ける）＋ MagicPod の画面での設定（一括実行の対象をラベルにする） |
| テストケースを増やす | スモークテスト作成・テスト設計のスキル |
| 毎日の一括実行を設定する、一括実行の設定を新しく作る、CI につなぐ | MagicPod の画面での設定（ヘルプ記事を案内する） |
| 失敗を通知で受け取る | MagicPod の画面での設定（ヘルプ記事を案内する） |
| テストを棚卸しして、使わないテストを削除する | テストスイート整理のスキル（削除の候補を理由つきで提案し、残すテストのラベル・フォルダ・名前を整える）。削除そのものはユーザーが MagicPod の画面で行う |
| メンバーを招待する | MagicPod の画面での操作（ヘルプ記事を案内する） |

- つなぎ先のスキルが入っていない場合は、ヘルプ記事と、画面での手順を案内する。
- 改善を始めたら、1週間後に同じスキルでスコアの変化を確認するよう勧める。
