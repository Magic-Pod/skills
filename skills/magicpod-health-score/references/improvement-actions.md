# 改善策の一覧

項目ごとに「減点の理由」「すぐできること（1〜2週間）」「時間をかけてやること（1〜3か月）」をまとめる。
提案するときは、プロジェクトの状況に合うものを選び、1項目につき1〜2個に絞る。

## 並べ方のルール

1. テストケースが 8 件未満 → 「テストケースを 8 件にする」を最初に置く。
2. 前の週よりスコアが下がっている → 「新しいテストの作成をいったん止め、既存のテストを直す」を先に置く。
3. それ以外は、伸びしろ（満点 − 現在の点数）が大きい順。同じくらいなら、すぐできるものを先に。
4. 提案は全体で 3〜5 件まで。

## 項目ごとの改善策

### 実行頻度（35 点）

- 減点の理由：一括実行が毎日走っていない、または一括実行に入っていないテストがある。
- すぐできること：
  - 一括実行のスケジュール実行を、平日毎日に設定する。
  - CI（GitHub Actions、Jenkins など）から毎日、または開発のたびに一括実行する。
  - 作ったテストケースを一括実行の対象に入れる（入っていないテストは実行していない扱いになる）。
- 時間をかけてやること：開発チームを巻き込み、テスト結果を開発の流れの中で見る仕組みにする。

### 失敗率（35 点）

- 減点の理由：一括実行で失敗しているテストがそのままになっている。実行頻度が低いことでも減点される。
- すぐできること：
  - 失敗したテストを翌日に持ち越さず、その日のうちに直すルールにする。
  - すぐに直せない不安定なテストは、いったん一括実行から外す。外したテストは一覧にして、直したら戻す（外している間は実行頻度の点が下がることがあるので、一時的な対応にする）。
  - ただし、毎日失敗しているテストが全体の 1 割を超えるときは、外すだけだと実行頻度の点が大きく下がる。その場合は、外すより「実行していない古いテスト」の節の棚卸し（直して回す／やめる）を先に勧める。
- 時間をかけてやること：失敗の根本原因（待ち時間、テストデータ、環境）をつぶす。テストの担当者だけで直せないときのエスカレーション先を決める。
- 注意：失敗の原因の調査や修正は、このスキルでは行わない（SKILL.md の手順 6 でつなぐ）。

### 共有ステップ（8 点）

- 減点の理由：ログインなど、複数のテストで同じ操作をそれぞれに書いている。
- すぐできること：ログイン・ログアウトなど、よく使う操作を共有ステップにする。
- 時間をかけてやること：「今後使い回せそうなものは、今1か所でしか使っていなくても共有ステップにする」をチームのルールにする。
- 効果：画面が変わっても1か所直せば済み、直し漏れによる失敗を防げる。

### 安定したロケータ（8 点）

- 減点の理由：安定したロケータ（`scoring-logic.md` の 5 の定義）に当てはまらないもの、たとえば位置に依存する XPath を使っている。属性で要素が一意に決まる CSS セレクタや iOS class chain は安定として扱われるので、置き換えの対象にしない。
- すぐできること：返り値の一覧で不安定なロケータが多いテストケースから、id や属性・テキストで特定するロケータに置き換える。
- 時間をかけてやること：開発チームに、テストで使う要素へ id・属性を付けてもらうよう依頼する。

### テスト数（6 点）

- 減点の理由：テストケースが 20 件未満（8 件未満なら、ほかの項目にも補正がかかる）。
- すぐできること：主要なユースケース（ログインなど）から、壊れにくく毎日実行する価値のあるテストを足す。
- 時間をかけてやること：スコアを保ちながら、月に 2〜3 件ずつ増やす。

### メンバー数（3 点）

- 減点の理由：プロジェクトのメンバーが 4 人未満。
- すぐできること：テストを作る人だけでなく、**テスト結果を見てほしい人** をプロジェクトに招待する。
  - **マネージャー**：結果を見るだけでも、テストが健全に回っていることを確かめられる。
  - **開発メンバー**：テストのログを見て、バグの調査に生かせる。
- MagicPod はメンバー数が無制限なので、招待しても費用は増えない。費用を気にするユーザーには、このことを添える。
- 一人 QA やテストのチームがいない場合も、「人がいないから増やせない」で終わらせず、上のマネージャーや開発メンバーを招待するよう提案する。テストを作る・直す人を増やす話ではないと添える。
- 時間をかけてやること：メンテナンス担当を週番制にするなど、特定の人に頼らない体制にする。

### テストの長さ（5 点）

- 減点の理由：長いテスト（ブラウザ 300 ステップ以上、モバイル 200 ステップ以上）が全体の 10% を超えている。
- すぐできること：長いテストを、機能や画面の単位で分ける。
- 補足：長くせざるを得ないテストもあるので、満点の条件はそれほど厳しくない。

## スコアが上がりにくい、よくある状況

当てはまりそうなら、一般的な改善策より先に、ここの考え方で提案する。分からなければユーザーに聞く。

### アプリのリリース頻度が低く、テストを毎日実行する理由が見えにくい

- よくある考え：「リリースがない日にテストを回しても意味がない」。
- 提案：全部のテストでなくてよいので、**ラベルでメイン機能のテストを選び、それだけでも毎日一括実行する**。
  - 毎日回していないテストは、いざリリースの前に回すと、アプリや環境の変化で壊れていて直すのに時間がかかる。毎日回すのは、テストをいつでも使える状態に保つため。
  - 外部のサービスや環境（ブラウザのバージョン、テストデータ、証明書など）の変化にも早く気づける。
- 満点の条件は「全テスト、または 60 件以上を毎日」なので、テストが多いプロジェクトでは全部を回さなくても点が取れる。

### ローカルの実機でテストしていて、毎日の実行が難しい

- 見分け方：`list_batch_runs` の `test_condition_labels` で、環境のラベルがクラウド（`Cloud`）でない実行が中心になっている。
- 提案（順に検討する）：
  1. **クラウドで動くものを切り出す**：メイン機能のうち、実機でなくても確かめられるテストを、クラウド端末で毎日の一括実行に乗せる。
  2. **PC を1台占有できれば、ローカル実機でも毎日の一括実行を組める**。実機をつないだままにできる PC があるかを聞く。
  3. それでも難しい場合は、**目標を現実的にする**。グリーンにこだわらず、「メイン機能は毎日実行し、オレンジを保つ」などをチームの目標にする。スコアが低いのは「毎日のフィードバックがない」ことの表れなので、そのことは正直に伝える。

### 実行していない古いテストがたくさん残っている

- 作ったテストは、実行していなくても実行頻度の分母に入る。また、ずっと前のテストが放置されている状態は、メンテナンスの面でも健全ではない。
- 見分け方の目安（`list_test_cases` には最後に実行した日がないので、次から推し量る）：
  - ステップが 0 件のテスト
  - 「作成中」「WIP」のラベルが付いたまま、数か月 `updated_at` が変わっていないテスト
  - 名前や要約から、動作を試すために作ったと分かるテスト
  - 一括実行に入っていないと思われるテスト（ユーザーに確認する）
- 提案：**定期的に棚卸しをして、テストを「直して毎日回す」か「やめる」かに分ける**。
  - やめるテストのうち、また使うかもしれないものは、テストの内容（手順・確認すること）を残してから削除する。内容が残っていれば、必要になったときに MCP で作り直せる。動作を試すために作っただけのテストなど、自動化したい対象と関係ないものは、残さずに削除してよい。
  - テストを減らすと、20 件を下回ったときにテスト数の点（6 点）が、8 件を下回ったときにほかの項目の補正がかかって点が下がる。棚卸しの前に、残す件数と、そのときの点数の変化を伝える。一時的に下がっても、毎日の実行で取れる点（実行頻度・失敗率で 70 点）のほうがずっと大きいと添える。
  - 一時的に止めている機能のテストなど、残す理由があるものは、いつまで残すかを決めておく。
  - 削除は元に戻せない場合があるので、消す前に内容を残したかを必ず確認する。このスキルでは削除しない。
- テストが 60 件を超えるプロジェクトなら、残すテストのうち 60 件以上を毎日回せば実行頻度は満点になるので、棚卸しは「スコアのため」より「保守の負担を減らすため」として勧める。

## グリーンを維持する

スコアが 80 点以上のプロジェクトには、次の習慣ができているかを確認する。データから判断できるものは判断し、できないものはユーザーに聞く。

| 習慣 | データからの判断 |
|---|---|
| 平日毎日の一括実行 | `list_batch_runs` で、スケジュール実行や CI の実行が平日毎日あるか |
| 失敗を翌日に持ち越さない | `failed_or_incomplete_test_cases` で、同じテストが週に何回も失敗していないか。特定のテスト設定の一括実行が何日も続けて失敗していないか |
| 週1回のスコア確認・メンテナンスの時間 | データからは分からない。ユーザーに聞く |

- 週に1回、曜日を決めてスコアを確認する（定例ミーティングでチーム全体で見るとよい）。
- 失敗したテストは翌日に持ち越さない。毎朝、前日の結果を確認する。
- 毎週決まった時間（例：週2時間）をテストの改善にあてる。
- 何をしてスコアがどう変わったかを、チームで共有する。
- テストを増やすときは少しずつ増やし、スコアが下がったら増やすのを止めて既存のテストを直す。
- 応用：MagicPod の Web API でスコアを取得し、チャットツールへの通知や社内のダッシュボードに組み込むこともできる。
