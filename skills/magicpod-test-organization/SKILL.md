# MagicPod テストスイート整理（Test suite organization）

テストケースの **置き場所（フォルダ）・名前・ラベル・共有ステップ** を整え、テストを探しやすく、直しやすく、一括実行で狙ったものだけを回せる状態にするスキル。

## このスキルがやること・やらないこと

- **やる**
  - 現状の診断（命名のばらつき、フォルダ、ラベル、重複ステップ、使われていない共有ステップ、説明欄、一括実行に入っていないテスト）
  - 整理のルールの提案と決定、`MAGICPOD_CONVENTIONS.md` への書き出し
  - 承認を得たうえでの変更：テストケース名・説明の変更、フォルダの作成・移動、ラベルの付け外し、共有ステップの作成と置き換え、共有ステップの名前・フォルダの整理、使われていない共有ステップのゴミ箱への移動
- **やらない**
  - アプリの変更に合わせたテストの修正、失敗原因の調査、ロケータの修正
  - テストケースの削除（候補を挙げるだけ。削除はユーザーが画面で行う）。ステップをすべて消して実質的に空にするなど、削除と同じ結果になる操作もしない。AI が知らないうちにテストを消した、という事態を防ぐため、消す判断と操作は人が行う。
  - ラベルの作成・ラベルの説明の編集、一括実行の設定の変更（MCP ではできないので、ユーザーに画面で行ってもらう。手順は案内する）

## 前提

- MagicPod MCP サーバーに接続していること。接続していない場合は、ルールづくり（手順 4）だけを、ユーザーへの質問とテストケース名の一覧（貼ってもらう）をもとに進められる。
- 名前・説明・ラベル・フォルダ・共有ステップの変更は、**デフォルトブランチだけ** でできる（MCP の制約）。変更はすぐにチーム全員に見える。ブランチで試してから反映する、という進め方はできないことを、最初の変更の前に伝える。

## 守ること（すべての手順に共通）

1. **変更の前に、必ず一覧（変更前 → 変更後）を見せて承認を得る。** 承認の範囲を超えて変更しない。
2. **一度に変更するのは 20 件程度まで。** それより多いときは、フォルダごとなどに分けて、区切りごとに結果を見せる。
3. **変更前の状態を記録して、最後に変更の一覧を出す。** MCP には元に戻す機能がないので、手で戻せるようにするため（`references/report-template.md` の「変更の記録」）。
4. **実行範囲や実行順が変わる操作は、影響を先に伝える。**
   - 一括実行の対象をフォルダで指定していると、テストを別のフォルダに移しただけで実行範囲が変わる。
   - 一括実行はテストケース一覧の **上から順** に実行されるので、並べ替えると実行順が変わる。
5. **失敗したら同じ呼び出しを繰り返さない。** 同じ手順で3回失敗したら止めて、エラーをユーザーに伝える。
6. テストケースへのリンクは `https://app.magicpod.com/{組織名}/{プロジェクト名}/{テストケース番号}/` の形で組み立てる（返り値の URL はそのままでは開けないことがある）。

## 手順

### 1. 対象のプロジェクトを決める

- ユーザーが組織名・プロジェクト名、または MagicPod の URL を示していれば、それを使う。
- 示していなければ `list_organizations` → `list_projects` で候補を出して聞く。候補は `表示名（名前）` とプラットフォーム（ブラウザ／モバイル）を並べる。整理は1プロジェクトずつ行う。
- プロジェクトには、画面に出る **表示名** と、URL やツールの呼び出しに使う **名前**（内部名）の2つがあり、違うことがある。候補やまとめでは両方を `表示名（名前）` の形で出す（同じなら1つでよい）。ツールの呼び出しとリンクには名前を使う。

### 2. ルールのファイルを読む

- 今の作業フォルダ（Git リポジトリなら、その一番上のフォルダ）に `MAGICPOD_CONVENTIONS.md` があれば読む。`AGENTS.md` や `CLAUDE.md` に別の場所が書かれていれば、そこを読む。それ以外の下の階層までは探さない。なければ、ないものとして進める。節は英語の目印（`<!-- section: naming -->` など）で探す。
- ルールがあれば、**そのルールを既定より優先** する。手順 4 は、足りない部分だけ決めればよい。
- ファイルのルールと MagicPod の実際の状態が食い違っていたら（例：ルールにあるラベルがプロジェクトにない）、直さずに報告する。

### 3. 現状を集めて診断する（読み取りのみ）

ユーザーが特定の作業だけを頼んでいる（例：「共有ステップにまとめて」）ときは、その作業に必要なものだけを取り、診断の表は出さずに手順 5 の該当する節へ進む。

全体を整理したいときは、次を取得する。

| 取得するもの | ツール | 見ること |
|---|---|---|
| テストケースとフォルダ | `list_test_cases`（`depth: null`） | 名前、場所（フォルダ）、`labels`、`description`、`step_count`、`updated_at` |
| ラベル | `list_test_case_labels` | ラベルの一覧と説明 |
| 共有ステップ | `list_shared_steps`（`depth: null`） | 名前、フォルダ、`test_case_count` と `shared_step_count`（使われている数） |
| 一括実行で実際に動いたテスト | `list_batch_runs` → 設定ごとに直近の3〜5回を `list_batch_run_test_runs` | どのテストがどの一括実行で動いているか、毎回失敗しているテスト・ときどき失敗するテスト |
| 共有ステップを使っているテスト（必要なとき） | `get_shared_step` | `referencing_test_cases`（`list_shared_steps` の件数だけでは、どのテストで使われているか分からない） |

- `list_test_cases` の返り値は、1件ごとの要約（`ai_generated_summary`）を含んで大きい。テストが 100 件を超えるときは、フォルダごとに取る（`folder_number`）。
- `list_test_settings` からは、一括実行の対象（フォルダ・ラベル・番号の指定）は分からない。実際に動いたテストは一括実行の結果から読む。対象の指定のしかたは、ユーザーに聞く（画面の「実行対象」タブで確認できる）。
  - 対象の指定のしかたは、動いた件数とテストの全件数を比べると見当がつく（全件が動いていれば「全件」か、全部が入ったフォルダの指定。ラベルの付いたテストが0件なのに動いていれば、ラベルでは指定していない）。見当をつけたうえで、画面の「実行対象」タブを確かめてもらう。
  - 直近の数回を比べて、**毎回失敗しているテスト**（壊れたまま。ラベル整理のときに一括実行の対象から外す候補）と、**ときどき失敗するテスト**（Flaky の候補）を分ける。**一括実行の設定によって結果が違うテスト**（ある設定では成功し、別の設定では毎回失敗する）も挙げる（設定から渡す変数の違いなどが考えられる）。失敗の原因は調べない。
  - 一括実行の結果を選ぶとき、リトライの実行（設定名が `[#N のリトライ] …` のもの）は除く。設定名が空のもの（コマンドラインで設定を使わずに実行したものなど）は、動いたテストの番号が読めれば使い、読めなければ使わずに「読めなかった」と書く。
  - 定期実行が途中で止まっていれば（最後の実行日）、診断に書く。
- 返り値のテストケースの URL（`web.prod.local…` など）はそのままでは開けない。リンクは「守ること」の 6 の形で組み立てる。

診断は `references/report-template.md` の「診断」の形でまとめる。見る観点：

| 観点 | 例 |
|---|---|
| 命名 | 形がばらばら、同じ名前のテストが複数ある、「Test」「ほげ」など中身が分からない名前 |
| フォルダ | フォルダがない（すべて一番上）、3階層以上、用途や状態（スモーク、作成中）のフォルダ、テストが1件だけのフォルダ |
| ラベル | 意味の分からないラベル、同じテストに矛盾するラベル（「作成中」と「完成」など）、ほとんど使われていないラベル、フォルダと同じ軸のラベル |
| 共有ステップ | 使われていない共有ステップ、似た名前の共有ステップ、名前の付け方がばらばら |
| 重複ステップ | 同じ手順（ログインなど）が複数のテストにそのまま書かれていそう（名前や要約から推測。確認は手順 5-4 で行う） |
| 説明欄 | 説明が空のテストの割合 |
| 一括実行 | どの一括実行でも動いていないテスト、毎回失敗しているテスト、ときどき失敗するテスト |
| 棚卸しの候補 | ステップが 0 件（一括実行では「成功」と数えられ、成功率を実際より高く見せてしまう）、長く更新されていない、名前から試しに作ったと分かるもの、コピーのまま残っているもの（名前に `Copy` など） |

最後に、どれから進めるかを聞く。勧める順は次のとおり（ルールが先、変更の多いものは後）。

1. ルールを決める（手順 4）
2. ラベル（一括実行の対象をラベルで管理できるようにする）
3. フォルダ
4. 命名・説明欄
5. 共有ステップ（重複ステップのまとめ、共有ステップの片付け）

### 4. ルールを決める

`references/rules-and-conventions.md` に沿って、命名・フォルダ・ラベル・一括実行・共有ステップのルールを決める。

- 既存のテストから案を作って示し、ユーザーに選んでもらう。一度に聞くのは3問まで。聞かなかった項目（共有ステップ、一括実行など）は案として示し、まとめて承認を得る。
- 最初の質問で、**命名とフォルダ名の言語**（日本語・英語・英語の接頭辞＋日本語）を一緒に決める。あとから片方だけ変えると、名前の頭をフォルダ名にそろえるルールが崩れる。
- ユーザーが自分の命名規則を持っていれば、それを使う。
- 決まったら、`MAGICPOD_CONVENTIONS.md` に書き出す（書き出す前に中身と置き場所を見せて承認を得る）。あわせて、`AGENTS.md` と `CLAUDE.md` に参照の1行を入れるかを聞く（`references/rules-and-conventions.md` の「ルールのファイル」）。
- 次に進めるのがラベルなら、ルールのファイルの承認とラベルの計画の承認を1回にまとめてよい（往復を減らすため）。

### 5. 整理する（承認を得てから変更）

それぞれ「計画を見せる → 承認 → 変更 → 結果を確かめる」の順に進める。

- **変更の前に、ルールのファイルを書き出す。** ユーザーが手順 4 を飛ばして整理から始めたときも、計画を作る中で決めたルール（命名の形、名前やフォルダの言語、ラベルなど）があり、`MAGICPOD_CONVENTIONS.md` にまだ書かれていなければ、そのルールを `MAGICPOD_CONVENTIONS.md` に書き出す案を、計画と一緒に見せる。承認は1回にまとめてよい。書き出してから MagicPod を変える。
- 書き出さなくてよいと言われたら、書き出さずに進め、手順 6 の報告に「ルールのファイルは書き出していない」と書く。

#### 5-1. ラベル

1. ルールに沿って、テストごとに付けるラベル・外すラベルの計画を作る。診断で「毎回失敗している」と分かったテストは、毎日の実行のラベルを付けず、直すまでの印のラベル（例：`要修正`）を付ける案にする。
2. 計画と、新しく作るラベル（名前と説明欄の文の案）を見せて承認を得る。
3. **プロジェクトにないラベルは、ユーザーに画面で作ってもらう**（MCP では作れない）。手順（プロジェクトの 設定 > テストケースラベル > 追加）を案内する。既存のラベルの名前を変えたいとき（誤字など）も、画面で直してもらう。
4. 作ったと言われたら `list_test_case_labels` で、**名前と説明欄の両方** を確かめる（説明欄の写し間違いなどがあれば伝える）。
5. `manage_test_cases`（`action: "update_labels"`）で付け外しする。1回に 100 件まで。同じラベルを付けるテストをまとめて1回で行う。
6. 一括実行の対象をラベルで指定するよう、画面での設定の変更を案内する。複数のラベルを選ぶと「どれかが付いているテスト」が対象になること、フォルダとラベルを両方指定すると「両方に当てはまるテスト」になることを伝える。

#### 5-2. フォルダ

1. **移す前に、一括実行の対象をフォルダで指定しているかを聞く。** 指定しているなら、先にラベルでの指定に切り替えるか、移したあとに設定を直すかを決めてもらう。
2. 新しいフォルダ構成（2階層まで）と、テストごとの移動先を表で示す。
3. `manage_test_cases`（`action: "create_folder"`）でフォルダを作り、`reorder_test_case`（`action: "move"`）でテストを1件ずつ移す。
   - 既存のフォルダを新しい構成のどれかに使い回せるなら、作り直さずに `rename_folder` で名前を変える（作成と削除の手間が減り、中のテストの並びも保てる）。
   - 新しいフォルダは兄弟の **末尾** に作られる（返り値の `order`）。先頭などに置きたいときは、作ったあと `move`（`resource_type: "FOLDER"`）で動かす。
   - 複数のテストを同じフォルダに移すときは、`position` に移し先の今の件数を入れて、末尾に順に足していく。
   - 全体を一度に並べ替える `bulk_update` は、すべてのフォルダとテストを漏れなく書く必要があり、漏れると構成が崩れる。使うのは、移す件数が多く、ユーザーが了承したときだけにする。
4. 空になった古いフォルダは、ユーザーの承認を得てから `delete_folder` で消す（空のフォルダしか消せない）。
5. 移したあと `list_test_cases` で構成を確かめ、一括実行の実行順が変わったテストがあれば伝える。

#### 5-3. 命名・説明欄

`references/naming.md` に沿って進める。

1. ルールから外れているテストを洗い出し、変更前 → 変更後の表を見せる。名前から中身が分からないものは、`ai_generated_summary` やステップの内容（`get_test_case_detail`）を読んで案を作る。
2. 承認を得たものだけ、`manage_test_cases`（`action: "update_test_case"`、`name`）で変える。
3. 説明欄が空のテストには、ステップの内容から説明の案を作り、同じように承認を得てから `description` で書き込む。

#### 5-4. 共有ステップ

`references/shared-steps.md` に沿って進める。

- **重複ステップのまとめ**：候補のテストのステップを読み、同じ手順の並びを見つけて、共有ステップにする計画（名前、パラメータ、置き換えるテストと範囲）を示す。承認を得てから、1件目のテストで `create_shared_step` を使って作り、残りのテストの同じ範囲を、作った共有ステップの呼び出しに置き換える。最初の1件で動くことを確かめてから、残りに広げる。
- **共有ステップの片付け**：使われていないもの（`test_case_count` と `shared_step_count` がどちらも 0）、似たもの、名前がルールから外れているものを挙げる。承認を得てから `manage_shared_steps` で名前の変更・フォルダ分け・ゴミ箱への移動を行う。

### 6. まとめる

- `references/report-template.md` の「完了の報告」の形で、やったこと・変更の記録・残っていること（ユーザーが画面で行うこと）をまとめる。
- ルールを変えた・足したときは、`MAGICPOD_CONVENTIONS.md` を更新する（差分を見せて承認を得る）。整理の途中で決めたルールがまだ書き出されていなければ、ここで書き出しを提案する。
- **棚卸しの提案を、完了の報告に必ず入れる。** 削除してよさそうなテストを、理由と区分（削除をおすすめ／判断が必要／残して直す）つきで示す。見る観点は `references/report-template.md` の「棚卸しの提案」。
  - テストケースの削除はユーザーが画面で行う。削除の前に、`get_test_case_detail` で読んだステップを控えとしてファイルに残せることを案内する（MCP には書き出しの機能がない）。
  - 使われていない共有ステップは、承認を得ればこのスキルでゴミ箱へ移せる（5-4）。
- 整理と関係のない問題に気づいたとき（URL に資格情報が直接書かれている、何も確かめていないテストなど）は、直さずに「気づいたこと」として報告に1〜2行で書く。
